## [1.29.0] — 2026-10-26

### Исправлено

- **«Доменов нет» писалось там, где конфиг не читался.** Прежний вид
  (`common.get_domain_from_config`):

      grep -h 'server_name' {путь} 2>/dev/null | sed … | tr … | grep -v …

  Терялись ТРИ вещи сразу — ровно как в 1.28.0 на systemctl. `2>/dev/null`
  глушил единственную строку, где написано ПОЧЕМУ пусто. Пайп **забирал код
  возврата**: конвейер отдаёт rc последней команды (`grep -v`), а тот сообщает
  лишь «фильтр что-то пропустил / не пропустил» — про права пайп не говорит
  НИКОГДА. Третья потеря: вывод был УЖЕ извлечёнными именами, поэтому тестовый
  двойник описывал ответ, которого `grep` не выдаёт никогда, и чинить пайп под
  зелёными тестами было нельзя (урок 1.27.0).

  Замер живьём (этот хост, uid=1000, `/bin/bash`), новая форма — ОДНА команда
  `grep -h 'server_name' ПУТЬ 2>&1`, rc принадлежит grep'у:

      читаемый, домены есть      rc=0  server_name example.com www.example.com;
      прочитан, server_name нет  rc=1  (пусто)          — честный ответ системы
      ЗАКРЫТ 0000                rc=2  grep: …: Permission denied
      ОТСУТСТВУЕТ                rc=2  grep: …: No such file or directory
      КАТАЛОГ                    rc=2  grep: …: Is a directory

  Прежняя пайп-команда на трёх последних состояниях давала rc=1 и пустой
  вывод, идентичный честному «прочитан, `server_name` нет», то есть `[]`.
  «Нет прав на конфиг» и «конфига нет» — противоположные действия (поднимать
  права против менять раскладку панели) — были одним ответом, и
  `get_domains_info` докладывал «доменов нет». Именно этот список кормит все
  отчёты (`site_logs_report`, «Проверка доменов» в GUI).
- **Парсер `server_name` врал содержимым, а не только причинами.** Прежний sed
  с жадным `.*server_name` на настоящих файлах (замер живьём):

      '#    server_name uhatil.tld;'          -> ['uhatil.tld']   домен из комментария
      '   # server_name staryj.tld;'          -> ['staryj.tld']   домен из комментария
      'server_names_hash_bucket_size 128.0;'  -> ['128.0']        это НЕ server_name
      'server_name hodovyj.tld; # …ljevoj;'   -> ['ljevoj.tld']   настоящий ПОТЕРЯН

  Последняя строка — двойная ложь: жадный `.*` брал ПОСЛЕДНИЙ `server_name`
  строки, поэтому конфиг с закомментированной строкой ниже терял реальный
  домен и получал выдуманный. По таким именам отчёт шёл читать
  `/var/log/nginx/128.0.error.log`. Извлечение переехало на python
  (`domains_from_config_text`): комментарий не директива (`#` в начале строки
  и в её хвосте), директива опознаётся по префиксу С ГРАНИЦЕЙ слова, фильтр
  унаследован от прежнего пайпа (`*`-шаблоны, `_`, `localhost`,
  `default_server`, всё без точки — не домены).
- **Отчёт тонул в признаниях: десять закрытых конфигов = десять одинаковых
  строк.** Показал первый GREEN этого слайса (замер живьём): причина дошла до
  оператора — но десятью строками, а признание, которого десять, оператор
  перестаёт читать. Теперь сводка ОДНА на основание и называет масштаб:
  `⚠️ Домены по 10 файлам (…site0.conf и ещё 9): нет прав на файл конфига…`.
  При этом «нет прав» и «нет на сервере» не сливаются (лечения
  противоположные), и разные ответы системы («memory exhausted» против
  «input file is also the output») остаются раздельными: это разные
  основания, и каждый цитируется.
- **Цитата системы калечилась при вырезании пути.** Живой контроль на
  настоящем `/bin/bash` показал `(grep:: Permission denied)`: путь вырезан,
  а дыра по шву осталась. Первую правку (`replace(' : ', ': ')`) я сделал сам
  и она прорезала дыру глубже — `grep: :` доканчивалось до `grep::`.
  Правильно сворачивать сам шов; закрыто тестом
  `test_system_answer_is_quoted_without_a_hole`.

### Изменено

- Команда чтения конфига — ОДНА `grep` без пайпа с `2>&1`: rc принадлежит
  grep'у, stderr не глушится. `get_domain_from_config_info` возвращает
  (домены, notes); `domains_from_configs_info` — сводка по списку конфигов;
  публичная `get_domain_from_config` сохраняет прежнюю форму (только список).
  В `diagnostic.py` реэкспорт прежний, `_info`-формы не реэкспортируются
  (закон 1.24–1.28: внешний контракт не меняется).
- `logs.get_domains_info` собирает конфиги по всем паттернам `DOMAIN_PATHS`,
  дедуплицирует список и читает его ОДНИМ вызовом агрегатора: найденный
  конфиг больше не перечитывается заново под каждым паттерном.

## [1.28.0] — 2026-10-24

### Исправлено

- **«Служба панели не найдена» писалось на ЛЮБОМ хосте без systemd.** Прежний
  вид (`panels.py`):

      out, _, _ = checker.run(f'systemctl cat {q(unit)} 2>/dev/null | head -1')
      if out.strip():
          return unit

  Тут терялись ДВЕ вещи сразу. `2>/dev/null` глушил единственную строку, где
  написано ПОЧЕМУ пусто. А `| head -1` ещё и забирал себе код возврата: пайп
  отдаёт rc последней команды, то есть `head`, а он доволен всегда. Замер
  живьём (этот хост, `PID1=bwrap`, systemd нет, uid=1000):

      systemctl cat fastpanel2-engine       2>/dev/null | head -1 -> rc=0 stdout=''
      systemctl cat definitely-no-such-unit 2>/dev/null | head -1 -> rc=0 stdout=''
      systemctl cat fastpanel2-engine       2>&1                  -> rc=1
          'System has not been booted with systemd as init system (PID 1).
           Can't operate. / Failed to connect to bus: Host is down'

  То есть `fastpanel_unit` возвращал `None` и на «юнита нет», и на мёртвый
  systemd, и на отсутствующий бинарник, и на молчаливый сервер. Живой прогон
  против настоящей оболочки: `fastpanel_unit` → `None`, `fastpanel_restart` →
  «❌ Служба панели не найдена (fastpanel2-engine / fastpanel)», `systemctl
  restart` НЕ отправлен (4 команды ушло, перезапуска не было). Оператор шёл
  переустанавливать панель там, где надо смотреть доступ к systemd — этот отчёт
  самый ответственный в серии, по нему решают про переустановку.
- **`rc=127` не имеет права становиться «юнита нет».** Оболочка на отсутствующий
  бинарник печатает «No such file or directory» — тот же маркер, которым systemd
  отвечает на «юнита нет». Поэтому разбор идёт по rc ПЕРВЫМ (`rc=127` →
  «не проверено») и только потом по текстовым маркерам. Заперто тестом
  `test_missing_binary_wins_over_its_own_text` и живым прогоном классификатора.
- **Логи панели: «нет прав» больше не выдаётся за «логов нет».** Прежний вид:

      out, _, _ = checker.run(f'ls -1 {pattern} 2>/dev/null | head -{limit}')

  Замер живьём на четырёх состояниях каталога логов показал, что прежняя
  команда даёт `rc=0 out=''` одинаково на пустом, закрытом `0000` и
  отсутствующем каталоге — то есть отчёт «⚠️ Логи панели не найдены по путям»
  печатался и при закрытом каталоге, где лечение противоположное (поднимать
  права, а не проверять раскладку панели).

### Изменено

- `systemd_unit_state(out, err, rc) -> (состояние, причина)` — три разных
  диагноза вместо одного `None`: `unit` (rc=0 + непустой stdout), `absent`
  (так ответила система: «юнита нет»), `unknown` (бинарника нет / bus мёртв /
  сервер молчал / текст незнакомый). Незнакомый текст НЕ превращается в
  диагноз — не выдумываем то, чего не знаем.
- `fastpanel_unit_info(checker) -> (юнит | None, признание | None)`. Второе
  поле — не «причина отсутствия», а признание НЕПРОВЕРЕННОСТИ: его нет, когда
  система ответила (нашла юнит либо ответила «его нет»), и оно есть, когда
  спросить не получилось. Складывать это в одно значение нельзя: у «панели нет»
  и «мы не смогли посмотреть» противоположное лечение. `find_fastpanel_logs_info`
  — та же форма; обе `_info`-функции **не** реэкспортированы (их зовёт только
  свой модуль, закон 1.24–1.27), публичные `fastpanel_unit` /
  `find_fastpanel_logs` сохранили прежнюю форму.
- Команда поиска юнита: `systemctl cat ЮНИТ 2>&1` без пайпа — rc обязан
  принадлежать systemctl. Запертый тест `bash -n` новую команду принял.
- Четыре отчёта переведены на основание отказа: `fastpanel_restart`,
  `fastpanel_status`, `fastpanel_diag`, `fastpanel_logs`. Признанное ≠
  подтверждённое отсутствие: при непроверенном прогоне строка «не найдены» из
  вывода убрана совсем (иначе ложь просто переехала бы в соседнюю строку того
  же отчёта), а пути просмотра оставлены — по ним и чинят.
- Поиск логов панели ведёт примитив `find_files_info` (1.20.0) — **одной
  командой на путь, как и раньше**, поэтому различение состояний не подорожало.
- Пустой **прочитанный** каталог логов жалобы не даёт: «логов нет» — честный
  ответ, шум обесценил бы настоящие предупреждения (то же решение, что в
  1.24.0–1.27.0). Ответ «ни один путь не подтверждён» признаётся **одной**
  строкой на прогон, а не на каждый путь.

  это дало 3 «лога» из одного). Это артефакт подмены, а не дефект HEAD; в
  реальной системе прежний код получал бы ответ от `ls`.

## [1.27.0] — 2026-10-24

### Исправлено

- **Редактор конфигов снова работает: он находил конфиги НИКОГДА.** Прежний вид
  (`files.py`):

      out, _ = checker.exec_command(f'ls -d {q(path)} 2>/dev/null && echo "exists"')
      if out.strip() == 'exists':

  Замер живьём (`uid=1000`, `/bin/bash`, настоящие файлы):

      ls -d /etc/hosts 2>/dev/null && echo "exists"  ->  "/etc/hosts\nexists"
      [ "$out" = exists ]                            ->  ложь ВСЕГДА

  `ls -d` печатает сам путь, `echo` идёт второй строкой, а `strip()` снимает
  только края. Значит `get_config_files` возвращал `[]` на ЛЮБОМ сервере — не
  только без прав, — а редактор честно рапортовал «Конфигурационные файлы не
  найдены» там, где все конфиги есть. Это не «неточность формулировки», а
  неработающая функция, и враньё её стоило дороже молчания: оператор по этому
  диалогу решает, что на сервере нечего править.
- **Почему тесты этого не видели: двойник говорил то, чего не бывает.** Маршрут
  `('ls -d', 'exists\n')` возвращал идеальный ответ, который настоящий `ls` не
  выдаёт никогда. Двойник переведён на реалистичные ответы примитива состояния
  каталога (пути + `FFCOUNT` + `FFDIR`), и мёртвая ветка сразу вспыхнула 28
  падениями. Урок записан в базу: **двойник обязан говорить языком системы, а
  не языком ожидания автора теста.**
- **`/etc/php/*/php.ini` терялся из редактора всегда**: glob экранировался
  через `q()`, а `ls` в кавычках ищет файл со звездой в имени, а не раскрывает
  его. Пути-шаблоны теперь уходят в оболочку буквально (как в примитиве
  `find_files_cmd`).
- **Каталог больше не предлагается как файл.** Пустой прочитанный каталог
  прежний код добавлял в список «конфигов» («иначе потеряются одиночные
  конфиги») — редактор открывал каталог как текст. Одиночный конфиг находится
  веткой файла и так; это ровно `isdir` из 1.21.0, дошедшее до GUI.
- **Пустой список обязан называть причину.** Диалог различает «файлов нет»

      'worker 4;\n'     -> 'worker 4;'      <<< потеря
      'a;\nb;\n'         -> 'a;\nb;'         <<< потеря
      'a;\n\n\n'         -> 'a;\n\n'         <<< потеря
      'a;\r\nb;\r\n'     -> 'a;\nb;'         <<< потеря (и \r тоже)

  Для лога это безразлично (его всё равно считают построчно), для редактора
  конфига — тихая порча: «открыл → Сохранить» переписывал файл короче оригинала.
- **Сохранение перестало двигать хвост файла.** `get(1.0, END)` добавляет к

  вовсе, и «Сохранить» без единой правки ДОПИСЫВАЛО в конфиг пустую строку; в
  файловом менеджере срезали `rstrip('\n')`, то есть все хвостовые переводы
  разом — файл `a;\n\n` (пустая строка в конце — часть файла) уходил на сервер
  как `a;`. Теперь снимается ровно один перевод, добавленный виджетом.

  неудачу («❌ Ошибка записи: …») с ❌, но редактор админки тут же показывал
  «Успех — Файл сохранён», а редактор файлового менеджера — «Готово»; админка
  ещё и помечала файл сохранённым, из-за чего «Закрыть» молча теряло правки.
- **Четыре отказа различимы.** `read_file` построен на `read_file_info`
  (v1.21.0): «не читается под этим пользователем», «файла нет на сервере», «по
  этому пути каталог», «состояние не проверено» — вместо одного `rc=1`, который
  сливает права и отсутствие.

  directory`. Семантика `timeout` измерена, а не взята из мануала: 124 — убит по
  таймауту, 127 — бинарника нет, 1 — команда упала, 0 — успех. Пустой вывод дают
  четыре ситуации с разным лечением; теперь у каждой своя строка, и ни одна не
  выдаёт вердикт про домен.
- **Таймаут больше не читается как «домена нет».** `rc=124` означает, что реестр
  молчал дольше 15 секунд (часть ccTLD отвечает так; исходящий порт 43 часто
  блокируют). Домен при этом может быть сколько угодно зарегистрирован — прежняя
  фраза отправляла оператора искать причину в домене, которого это не касалось.
- **Причина сбоя видна оператору.** При `rc!=0` печатается `Ответ системы:` —
  первая строка stderr (`connect: Network is unreachable` и т.п.), которую прежняя
  команда выбрасывала.

### Изменено

- **Вердикт «домен не зарегистрирован» произносит реестр, а не программа.**
  Такой ответ — НЕ пустой вывод; живые запросы к реестрам через TCP/43 дали
  `No match for "…COM".` (Verisign), `No entries found for the selected
  source(s).` (TcI, RU-CENTER), `Domain not found.` (nic.me), `This domain name
  has not been registered.` (Nominet). Отчёт показывает `ℹ️`-строку с цитатой
  реестра. Служебное `NOT FOUND` внутри записи зарегистрированного домена ложного
  «свободен» не создаёт: вердикт возможен только когда в выводе нет ни одного
  поля записи.
- **Пустой вывод при `rc=0` — отдельное состояние `❓` («состояние не проверено»),
  а не красное.** Проверено живьём: такое возможно; права говорить про домен у
  такого ответа нет.
- **Признак «запись есть» решается в одном месте** (`whois_record_lines`).
  Ранее он считался дважды — для вывода полей и заново при решении «свободен ли»,
  — это ровно тот разъезд, который лечат последние релизы: отчёт однажды начал бы
  утверждать «не зарегистрирован» над уже напечатанным полем `registrar:`.
- **`stderr` больше не глушится в команде** — замок поведенческий: `2>/dev/null`
  проверяется в **отправленной команде**, а не в исходнике.

### Тесты

- **+10 тестов (1365 → 1375 по diff'у `--collect-only`)**: `rc=127` не подписывается
  отсутствием домена, `rc=124` не подписывается ни «нет домена», ни «нет утилиты»,
  причина из stderr показывается, пустой вывод при `rc=0` — «не проверено», фразы

  boilerplate ARIN (Terms of Use) не превращается в вердикт, `2>/dev/null` нет в
  отправленной команде, цена прогона — одна команда.
- Прежний тест `test_empty_whois_error` запирал текст `❌ whois не установлен или
  домен не найден` — то есть **ту самую подпись, которая выбирала между двумя

## [1.16.0] — 2026-10-23

### Исправлено

- **«Проверка SSL-сертификата» больше не выдаёт «не проверено» за «истёк».**
  Вердикт строился строкой `'VALID' in out_days` из ВТОРОЙ команды
  (`openssl x509 -noout -checkend 0`), а её код возврата была выброшен. `timeout
  10`, отсутствие openssl на сервере, разорванное соединение дают пустой вывод —
  «VALID» в нём нет — и отчёт печатал «❌ Сертификат ИСТЁК». Оператор ехал
  перевыпускать сертификат, которого на этом порту, возможно, и нет. Это закон
  «не проверено ≠ провалено», нарушенный в худшую из сторон: ложная беда дороже
  честного «не видно». Теперь при пустом ответе — «это "не проверено", а не
  "истёк"».
- **Сертификат, умирающий завтра, больше не подписан «действителен».** Та же
  `-checkend 0` умеет отвечать только «истёк ли СЕЙЧАС», поэтому «осталось 3 дня»
  (Let's Encrypt живёт 90 — это «чинить сегодня») выглядело зелёным. Вердикт
  строится точным остатком и **теми же словами, что сводка доступности и «Досье
  домена»** (`discovery.cert_days_label`): две формулировки одной беды однажды
  разъехались бы, и оператор не узнал бы свою беду в другом отчёте.
- **Служебная строка `CERT=` не показывается оператору.** Ей дополнена команда
  ради точного остатка; в «сыром выводе openssl» она выглядела бы как поле
  сертификата. Отфильтровывается ДО решения «получены ли данные»: иначе наша же
  строка выглядела бы как ответ сервера, и «не удалось получить» промолчало бы,
  уступив место вердикту о сроке несуществующего сертификата.

### Изменено

- **Второй TLS-хендшейк удалён, а не добавлен новым запросом.** `notAfter` уже
  лежит в первом ответе (`-dates`), поэтому остаток добирается локальной `date` на
  сервере: одна сетевая проба на отчёт вместо двух. Дни считаем именно там — дата
  машины оператора к выпуску сертификата отношения не имеет (то же правило, что в
  `discovery.site_status_command`).
- **Не вычисленный срок — отдельное состояние `❓`, а не красное.** Редкий формат
  `notAfter` или отсутствие GNU `date` дают «срок действия не определён»: и
  зелёное, и красное в этом месте были бы догадкой, а догадка про сертификат
  стоит оператору вечера работы.

### Тесты

- **+8 тестов (1349 → 1357 по diff'у `--collect-only`)**: точный остаток в
  подписи, «умирает через 3 дня» не зелёное, не вычисленный срок ≠ «истёк»,
  недоступный сертификат ≠ «истёк», совпадение формулировок с

### Добавлено

- **«Досье домена» различает состояния SSL, а не печатает «истекает/нет».**

  — досье оставалось последним местом, где вилка была схлопнута.
  - **Формулировка взята ровно та же, что у сводки** (`❌ SSL ИСТЁК 4 дн. назад`):
    два отчёта обязаны называть беду одними словами, иначе оператор не узнает в

  - **Цена не изменилась**: подпись строится из уже снятой пробы — гард
    `count("printf 'HTTP=") == 1` на домен.

### Исправлено

- **`cert_days_label(None)` больше не выдумывает причину.** Прежняя подпись —

  порт открыт и `https` ответил `500` без рабочего TLS. У функции нет кода
  ответа, значит у неё нет права про него говорить; причина теперь даёт
  `no_cert_reason(https)`, где код есть: «https не отвечает» (чинят фаерволлом и
  прослушиванием 443) против «https отвечает без рабочего TLS» (чинят конфигом

- **Решение «показывать ли SSL-пометку» — в одном месте (`cert_note_state`).**
  Пока оно живёт и в печатающей функции, и в читателе пробы, сводка обязана
  однажды посчитать ❓, которого в строках нет (или промолчать о показанном):
  счётчик и строка перестали бы смотреться. Сводка и строка берут ответ из одной
  функции; в SSL-отчёте нижняя причина тоже больше не строит свою ветку `why`.

### Тесты

- **+9 тестов (1340 → 1349 по diff'у `--collect-only`)**: пять состояний

  🌐» не отвечало ни на одно из них.
  - **Счётчик ведёт состояние сверки домена, а не символ «🌐» в тексте.** Этот
    символ печатается в трёх несходных случаях — «зона разошлась», «публичные
    записи совпали», «сверить не удалось», — и подсчёт по подстроке дал бы
    число, которого нет: оператор прочитал бы «расходится: 7» там, где семь
    доменов просто не удалось проверить. Состояние (`diverged` / `same` /
    `unverified`) возвращается наружу тем же кодом, что напечатал строки, —
    вторая реализация учёта однажды начала бы противоречить первой.
  - **Число даётся со знаменателем** — «4 (сверено доменов: 25)»: четыре
    расхождения при одном сверенном домене и при двадцати пяти это разный объём
    работ, и «4» без знаменателя было бы манипуляцией. Считаются **только
    проверенные** домены: оставшиеся за `HEALTH_CHECK_LIMIT` в счётчик не
    попадают.
  - **Цена не изменилась**: сводка считается из уже полученных ответов —
    по-прежнему probe + 5 локальных + 5 внешних на сверяемый домен (заперто
    гардом `count('dig ') == 11`).

### Исправлено

- **Совпавшее больше не дублируется, непроверенное не прячется.** Отдельной
  строки «расхождений нет» в сводке нет намеренно: в теле каждого домена уже
  напечатано «🌐 сверка через 1.1.1.1: публичные записи совпадают», где назван
  даже резолвер; повтор оператор читает как невнимательность и перестаёт доверять
  выводу. Этот запрет держался запертым гардом «ровно одно сообщение» — и именно
  он поймал дублирование, которое принесла новая сводка, до релиза.
- **«Не удалось сверить» — отдельная строка с собственным числом**, а не плюс к
  предыдущему: 2 беды и 20 «не видно» это разные решения (чинить зону и поднимать
  резолвер), складывать их нельзя. Если сверки не было ни у кого (зоны внешние,
  смотреть нечего), сводка молчит: «расхождений нет» означало бы «мы проверили и
  всё чисто», чего мы не проверяли.

### Тесты

- **+10 тестов (1308 → 1318 по diff'у `--collect-only`)**: знаменатель
  «сверено доменов», запрет сводки для совпавших, отдельность «не удалось» и
  запрет сложения с расхождениями, молчание при отсутствии сверки, позиция
  сводки ДО списка доменов, учёт только проверенных доменов при `limit`,
  неизменная цена прогона. Попутно пересчитан гард «🌐-строк»: сводка тоже
  начинается с этого символа, поэтому тело и сводка считаются раздельно, — а
  тест «счётчик считает только проверенные домены» сначала молча проверял не то
  (за `limit` уходил домен с пустой зоной с обеих сторон, расхождения нет) и был
  переписан на домен, который фикстура действительно сверяет.

## [1.12.0] — 2026-10-23

### Добавлено

- **Отказ доставки подписан доменом отправления.** v1.11 отвечал «кому бьёт»
  (домены получателей), но оператор чинит свой домен, а не чужую почту: «письма
  отбивает Gmail» для него бесполезно, нужно «у домена lie.ru письма отбивают за
  SPF». Теперь в почтовой сводке печатается «По вашим почтовым доменам: lie.ru —
  2», а в SPF-отчёте — одна строка «отправители отказов — по вашим доменам:
  lie.ru — 1». Тикет закрывается именем домена.
  - **Отправитель берётся join'ом по queue-id, а не угадывается по тексту
    отказа.** В строке доставки его физически нет: `postfix/smtp` печатает
    только `to=, relay=, delay=, dsn=, status=`. Конверт живёт в ДРУГОЙ записи
    того же письма: `qmgr` — `from=<…>` в момент активации очереди, `pickup` —
    `uid=1001 from=<…>` при локальной отправке, `smtpd` — `sasl_username=` при
    авторизации; `cleanup` пишет только `message-id` и адрес конверта в лог не
    печатает (man cleanup(8)). Рядом с адресом печатается, чем он подтверждён,
    чтобы строка не выглядела догадкой.
  - **Три состояния различаются явно.** Адрес известен; `from=<>` пустой —
    автоответ и уведомление о недоставке, их нельзя приписать ни одному домену
    (это ответ, а не промах); записи о входе письма в очередь в прочитанное окно
    не попало — «не видно». Назвать третье «не ваш домен» значило бы оправдать
    домен ложью, а свести второе к первому — соврать про чужое письмо.
  - **«Ваш» домен берётся из инвентаря почты сервера, а не из догадки.**
    Пометка ставится только домену, названному панелью; если инвентарь для
    отчёта не запрашивался, так и пишется — «какие домены считать вашими, не
    проверялось». Отправитель при этом не теряется: «не проверяли, чей он» ≠
    «отправителей нет».
  - **Цена не изменилась: одно чтение лога на прогон.** Индекс отправителей
    строится из уже прочитанного фрагмента — «+одна строка в отчёте» не стоит
    «+одно чтение лога». Гарды «одно чтение» стоят и на снимке, и на дайджесте
    при нескольких доменах. Меню не разрослось: ни одного нового пункта.

### Исправлено

- **Короткие queue-id перестали молча теряться.** Первая граница идентификатора
  `{7,16}` не подхватывала идентификаторы старых версий postfix (4 символа —
  `AAA2`, `AAB0`), и привязка на таком сервере деградировала в «отправитель не
  определён». Оператор прочитал бы это как «письма не от наших доменов»: тихая
  потеря данных, притворившаяся выводом. Нижняя граница опущена до 4.
- **Служебные слова syslog больше не притворяются идентификаторами.** Короткая
  граница открыла дыру опаснее предыдущей: на позицию идентификатора встают
  `postfix/smtpd[9]: warning: queue is full`, `statistics:`, `fatal:`,
  `NOQUEUE:` (`warning` — семь букв, он проходил и в прежней границе). Принять
  `warning` за queue-id — склеить все warning-строки сервера в одно «письмо» и
  приписать ему чужой отказ. Ложный идентификатор хуже пропущенного: пропущенный
  честно печатается как «не определён», ложный врёт. Отсечено алфавитом —
  шестнадцатеричные цифры и заглавные буквы, как их печатает postfix.
- **Счётчики переведены на форму «сущность — число»** («Отправитель не определён
  — 1», «Писем без отправителя (from=<>) — 1», «скрыто отказов — 12»), как уже
  принятая в очереди («писем — 5»). Прежняя форма («Ещё 1 отказов») при одном
  отказе читается как ошибка, а две схемы счёта в одном снимке — как
  невнимательность.
- **Тавтология свёрнутого вывода убрана.** Когда ни один отказ не привязан к
  домену, строка начиналась словосочетанием «отправители отказов — отправитель
  не определён: 2», что выглядело сломанным выводом при настоящих данных;
  заголовок подстраивается под содержимое («отказы без привязки к домену — …»), а
  тире внутри строки остаётся ровно одним.
- **Догадка о причине убрана из вывода.** «Письмо из deferred, простоявшее
  дольше окна» — лишь один из вариантов (ещё ротация лога и просто короткое
  окно); факт один: записи нет в прочитанном фрагменте.

### Тесты

- **+45 тестов (1263 → 1308 по diff'у `--collect-only`)**. Отдельно закрыты:
  разбор queue-id на живых формах (старый короткий id, новый 10-символьный,
  11-символьный, префикс journald без `[pid]`) и на шуме, обязанном НЕ давать
  идентификатора (`warning:`, `statistics:`, `fatal:`, `connect from
  unknown[...]`, `NOQUEUE: reject:`, `daemon started`); чужой идентификатор из
  текста причины (`queued as …`) не подставляется вместо своего; три источника
  отправителя и приоритет первой записи; пустой конверт — ответ, а не промах;
  «нет записи в окне» ≠ «не ваш домен»; «нашим» домен признаётся только по
  инвентарю, при его отсутствии пометки нет и это сказано словами; компактная
  строка дайджеста — ровно одна; цена — по-прежнему одно чтение лога на прогон
  в каждом из двух отчётов.

## [1.11.0] — 2026-10-23

### Добавлено

- **«Доставка писем по логу» — отчёт объясняет причину, а не только считает
  очередь.** `mailq` отвечает «сколько писем стоит», но не отвечает «почему», а
  тикет «письма уходят в спам / не доходят» живёт именно в причине. Теперь
  последние строки лога разбираются (`to=`, `dsn=`, `relay=`, `status=`) и
  печатаются отказы с расшифровкой группы: «спам или блокировка репутации»,
  «DNS домена получателя», «нет соединения с портом 25», «отказ в релее / нужна
  авторизация», «адресата нет», «сервер загружен / временный отказ» — плюс
  домены получателей, которым бьёт, и счётчик показанных отказов.
  - **Причина берётся из текста приёмника, а не из догадки.** Иглы групп —
    дословные фразы, которые в скобках после `status=` печатает получатель.
    Gmail, например, пишет `unauthenticated mail was rejected, please learn
    about SPF` — то есть причина отказа встречается в одном логе с проваленным
    SPF. Распознать произвольную строку нельзя, и в этом случае печатается её
    оригинал, а не выдуманная причина: оператор понесёт клиенту ровно то, что
    напечатал приёмник.
  - **Подтверждение диагноза DNS — прямо в SPF-отчёте.** Короткий дайджест
    («причины отказов: спам или блокировка — 2 · DNS-беда уже ломает доставку»)
    отвечает на вопрос «это вообще сейчас кому-то бьёт?». Разбор один и тот же в
    обоих отчётах, различается только подача: два парсера однажды начали бы по-
    разному считать одни и те же строки.
  - **Источник лога печатается всегда**, когда текст есть: «почему в сводке
    пусто» и «откуда взялись эти строки» — первый вопрос оператора, и отвечать
    на него молчанием нельзя.

### Исправлено

- **Debian/Ubuntu перестали быть слепыми для почтовых отчётов.** Читался только
  `/var/log/maillog`; об этом честно говорил наш собственный текст («лог может
  писаться в `/var/log/mail.log`»), а тест прямо констатировал: «мы его не
  читаем». Признанная слепота всё равно оставляла оператора с «причину не
  нашли». Теперь выбор делает одна функция: `maillog` → `mail.log` →
  `journalctl -u postfix`.
- **Дубль чтения почтового лога уничтожен.** postfix-отчёт и тест отправки
  читали лог каждая своим кодом; у проекта уже есть обжог на парных
  реализациях, которые разъезжаются. Расхождение здесь выглядело бы как «в
  одном отчёте лог есть, в другом — логов нет» на одном сервере.
- **Ротация лога больше не обрывает чтение.** Цепочка `tail … || tail …`
  полагается на rc, а ротированный и пока пустой `maillog` даёт rc=0 с пустым
  выводом — второй путь не спросился бы никогда. Выбор идёт по `[ -s ]`, то
  есть по содержимому.
- **`-- No entries --` перестало считаться содержимым лога.** `journalctl` при
  пустом журнале отвечает не пустотой, а именно этой строкой — прежний код
  показывал её оператору как записям postfix.
- **Причина отказа больше не теряется на живом сервере.** Прежний шаблон
  требовал закрывающую скобку в конце строки, а postfix дробит многострочный
  SMTP-ответ (`550-…`) на несколько записей и rsyslog режет строку по `$MaxLine`
  — скобки там просто нет. Терялась причина, а вместе с ней и диагноз: кейс
  «Gmail отбил письмо за SPF» оставался голой строкой «письмо отбито».
- **Лог, который не найден, не читается как «писем не было» и не закрывает
  тикет ложным «отказов нет»**: печатается «лог не найден» с ручной проверкой
  `ls -l /var/log/mail*`.
- **Незнакомый `status=` не считается отказом** (чужой MTA, новая версия
  postfix): он показывается строкой «без знакомого status». Врать про беду,
  статус которой не понят, — тот же грех, что и «не проверено» → «в порядке».
- **Отсутствие отказов не подаётся как «чинить нечего».** Приёмник, режущий
  спам, письмо не отбивает: принимает с `250 Ok` и молча кладёт в спам — в логе
  отправителя этого нет вовсе. Сводка пишет это опровержение под счётчиком, а
  дайджест — под списком причин.
- **Обещание ручной работы, сделанной за оператора, снято**: текст «лог может
  писаться в /var/log/mail.log» после починки стал бы ложью — путь читается.

### Тесты

- **+61 тест (1202 → 1263 по diff'у `--collect-only`)**. Отдельно закрыты:
  цикл выбора файла проверяется **настоящим `bash`** по временным файлам
  (заглушка отвечает на команду целиком и «первый пустой, второй живой»
  сымитировать не может) — пустой ротированный `maillog`, отсутствующий файл,
  grep во втором файле, ограничение `tail`, кавычка в имени пути как один
  аргумент; запрет positional-чтения лога мимо общей функции поведением (счётчик
  ушедших команд, а не разбор исходника); Debian-путь в postfix-отчёте и в
  тесте отправки; пять живых форм причины отказа (полная, дроблёный Gmail-ответ,
  обрезанная rsyslog, хвост после скобки, вложенная скобка); «нет класса
  причины» ≠ выдуманный класс; DSN 4xx как объяснение повторной попытки;
  отсутствие отказа ≠ «в порядке»; цена — ровно одно чтение лога на прогон в
  сводке и в SPF-отчёте при трёх доменах.

## [1.10.0] — 2026-10-23

### Добавлено

- **Строки «🌐» — программа сама смотрит публичный DNS.** Раньше при локальной
  зоне отчёт лишь писал «сверьте вручную» и оставлял оператору риск ложного
  «SPF ✅»: он читает зелёное и останавливается, а публичная зона тем временем
  может быть пустой. Теперь отчёт повторяет те же запросы к публичному резолверу
  и печатает расхождения строками «🌐 … извне»; если расходится всё, так и
  выглядит, если зона совпала — сообщается об этом одной строкой, а не
  молчанием.
  - **Вердикт, иконки шапки и подсказки «что вставить» считаются по ПУБЛИЧНОЙ
    картине.** Письмо судит приёмник, который видит DNS интернета, а не файл
    нашей зоны. Локальные строки при этом остаются напечатаны — по ним ищут, где
    именно зона разошлась.
  - **Внешние ответы разбираются теми же парсерами, что и локальные**
    (`external_parseds`). Второй набор правил однажды начал бы спорить с первым:
    «извне SPF нет» и «SPF в порядке» про одну и ту же запись оператор читает
    как «отчёт врёт».
  - **Сравниваются `status`, `reason` И `detail`.** Ограничиться первыми двумя
    было бы подтасовкой: две SPF-записи бывают одновременно `ok` и при этом
    разными (`ip4:1.1.1.1 -all` против `a ~all`), а оператору важно видеть, что
    публичная зона старше той, что он правит в панели.
  - **Сверка платит только там, где ложь возможна**: ещё 5 запросов на домен
    идут лишь у доменов с локальной зоной или локальным резолвером, причём
    условие и текст пометки берутся из одной функции — иначе «где сверять» и
    «где напечатано, что сверять надо» разъехались бы. Жив ли резолвер
    спрашивается **один** раз на прогон, а не на домен.
  - **Probe обязан спрашивать заведомо живое имя**: домен с пустой зоной
    отвечает так же пусто, как недоступный DNS, и по запросу к самому домену
    «жив ли DNS» не отличить. Признаком жизни считается ответ-адрес, а не
    «непустой вывод» — иначе любой мусор в stdout сошёлся бы за подтверждение.
  - **Внешний PTR берётся по ВНЕШНЕЙ A-записи**: локальная A тоже врёт (`10.x`
    из локальной зоны), а проверять обратную запись по адресу, которого в
    интернете нет, — выдумывать вердикт про чужую in-addr зону. Побочный эффект
    приятный: подсказка SPF теперь строится по публичному адресу, а не по
    приватному.

### Исправлено

- **Ложь, которую вскрыл живой прогон в собственной новой команде**: positional-
  форма `dig A name 1.1.1.1` адрес сервером не считает — запрос уходил на
  **местный** резолвер и отвечал за 0.0 с даже при заведомо мёртвом IP. Оставь
  это как есть, «сверка извне» печатала бы локальную зону с подписью «из
  интернета» — ровно ту ложь, ради исправления которой она и пишется. Резолвер
  задаётся строго через `@server`.
- **«Не получили ответ» перестало быть «записей нет».** При недоступном
  резолвере `dig` возвращает rc=9 и пишет `;; communications error` в **stdout**
  (`2>/dev/null` от этого не спасает), а честный пустой ответ — это rc=0 и
  молчание. Решение принимает rc, напечатанный самой командой; `;;`-строки
  отсекаются (в DKIM-цикле ошибка приклеена к имени после `|` — отсечена и эта
  вариация), иначе текст ошибки ушёл бы в парсер TXT как значение записи.
- **rc внешнего DKIM-цикла — флаг по всему циклу**, а не код последней команды:
  код последней молчит о предыдущих, и одна таймаутная итерация выглядела бы как
  «извне записей нет». Сверка, которая врёт про чужой DNS, хуже отсутствия сверки.
- **У внешнего PTR появился собственный признак ответа.** Общий признак его не
  покрывал (он зависит от внешней A и идёт пятым), и таймаут по `-x` давал
  «для 93.184.216.34 обратной записи нет» (❌) на основании недоступного DNS.
  Теперь PTR различает три состояния: «нечего спрашивать», «спросили, ответа
  нет», «честный пустой ответ» — последнее и только оно остаётся ❌.
- **Непроверенное больше не выглядит как «в порядке».** Если сверка домену была
  нужна, но не состоялась (резолвер жив, а по домену не ответил — или живых
  публичных резолверов нет вовсе), домен помечается `[не сверено]` и получает
  warn вместо ok, а рядом печатается команда ручной сверки. Понижения строгости
  нет: поднимается только ok, bad остаётся bad.
- **Команда ручной сверки не обещает оператору работу, сделанную за него**: она
  остаётся в пометке только там, где свериться самим не удалось. Формулировка
  пометки нейтральна умышленно — «сверка выполнена» было бы ложью, когда
  резолвер жив, но по домену мы не ответили.

### Тесты

- **+43 теста (1159 → 1202 по diff'у `--collect-only`)**. Отдельно закрыты:
  резолвер строго через `@` (и отсутствие positional-формы), обязательная

## [1.9.0] — 2026-10-23

### Добавлено

- **Строка «→» — что именно вставить в DNS.** Отчёт v1.8.0 отвечал на вопрос
  «где чинить», а оператора интересовал другой: «что вставить». Теперь под
  каждой проваленной проверкой домена печатается конкретная строка: готовая
  SPF-запись, готовая DMARC-запись, указатель, где взять настоящую DKIM-запись,
  и «запросить PTR у хостера» с уже подставленным адресом.
  - **Подсказки ветвятся по машинночитаемому коду беды (`reason`), а не по
    тексту отчёта.** У `parse_spf` / `parse_dkim` / `parse_dmarc` появилось поле
    `reason` (`missing`, `duplicate`, `too_many_lookups`, `plus_all`,
    `no_mechanism`, `broken_version`; `revoked`, `short_key`; `no_policy_tag`,
    `monitoring`, `no_rua`). Формулировки отчёта правятся ради читаемости, и
    подсказка, привязанная к фразе, отвалилась бы **молча** — показала бы
    оператору неверную запись, а он скопировал бы её в зону. Закрыто тестом,
    который портит `detail` и требует, чтобы совет остался.
  - **DKIM не генерируется никогда — это граница честности, а не лень.**
    Публичная TXT выводится из приватного ключа, который живёт на сервере.
    Выдуманная «готовая запись» означает подпись, которую приёмник отвергнет, а
    оператор решит, что «всё сделали». Вместо неё подсказка говорит, ГДЕ взять
    настоящую: включение подписи в панели либо ключи MTA (обычно
    `/etc/rspamd/dkim`, `/etc/opendkim/keys/<домен>/`), брать `.txt` и никогда
    не `.key` — там приватный ключ, публикация его в DNS была бы полной
    компрометацией подписи.
  - **SPF собирается из фактов этого же прогона** (A-запись → `ip4:`, иначе `a`)
    и всегда с `mx` и `~all`, а не `-all`: жёсткий запрет отклоняет письма CRM и
    рассылок, которых оператор ещё не внёс в запись. Основание записи печатается
    рядом и обязано описывать ровно тот механизм, что попал в строку.
  - **DMARC начинается с `p=none` + `rua` на сам домен.** Поднять сразу
    `reject`, не имея сводок, — дать приёмнику право убивать письма, о которых
    ничего не известно; а `rua` на чужой домен приёмник верифицирует отдельным
    DNS-тестом, и «настроенная» сводка не приходила бы никогда.
- **Подсказки не стоят ни одного дополнительного DNS-запроса**: строятся из
  уже полученных ответов, включая A-запись. Цена прогона осталась прежней —
  5 запросов на домен.

### Исправлено

- **Ложная подпись под SPF-подсказкой, которую вскрыл собственный прогон.**
  Первая версия печатала `v=spf1 a mx ~all` с пояснением «из A-записи домена»,
  хотя A-записи не было. Оператор такую подпись проглатывает не глядя. Введён
  `spf_basis(ip)`: механизм и его основание возвращаются вместе, поэтому
  подсказать одно, а объяснить другое стало нельзя.
- **Приватный адрес больше не предлагается как `ip4:`.** Если A-запись домена
  показывает `10.x`, `192.168.x`, `172.16–31.x` или `127.x` (сервер обслуживает
  локальную зону, домен за NAT), публичный SPF с `ip4:10.0.0.5` не совпадёт ни с
  одной сессией — приёмник смотрит на адрес TCP-соединения. Раньше это
  выглядело как рабочий совет, а по факту было заведомо мёртвой записью; теперь
  там механизм `a` с объяснением «публичный IP отправки сверьте у хостера».
- **Формат SPF-записи живёт в одном месте.** Подсказка печатает
  `spf_suggestion(ip)`, а не пересобирает строку у себя: две копии одной записи
  однажды разъехались бы, а оператор копирует в зону именно строку из подсказки —
  разойдись формат, в зоне оказалась бы не та запись, которую мы объясняли.
- **Один совет в отчёте один раз.** Общий блок «Как чинить» начал повторять то,
  что теперь подробно написано в «→ DKIM» у каждого домена; в нём остались рамка
  и указатель «копируйте строку «→»», а пути MTA переехали в подсказку.
- **У уже настроенного домена подсказок нет вообще**, и PTR-совет не печатается,
  когда PTR не проверялся (не было IPv4): «запросить обратную запись для » с
  пустым адресом было бы враньём. Пустой блок честнее советов про то, что
  работает.

### Тесты

- **+34 теста (1125 → 1159 по diff'у `--collect-only`)**. Отдельно закрыты:
  привязка подсказки к `reason` (текст `detail` портится — совет обязан

## [1.8.0] — 2026-10-23

### Добавлено

- **Письма уходят в спам: проверка SPF / DKIM / DMARC / PTR** — «🌐 Хостинг ▾ →
  Почта: SPF/DKIM/DMARC/PTR». Самый частый тикет хостинга («почта работает,
  письма уходят в спам») решается не в postfix, а в DNS, и проверка сделана
  именно как DNS-проверка: ни одной команды панели, только `dig`, который
  проект уже использует в досье домена. Поэтому пункт работает и на сервере без
  панели. На домен — 5 запросов (A, TXT, `_dmarc`, цикл по селекторам DKIM,
  PTR) и тот же лимит 25 доменов, что у проверки доступности сайтов.
  - **DKIM проверяется перебором селекторов.** Запись живёт в
    `<selector>._domainkey.<domain>`, а получатель ищет её по тегу `s=` из
    заголовка `DKIM-Signature` — значит проверить одно имя и сказать «DKIM нет»
    значит наврать. В списке `dkim` (FASTPANEL, kb.fastpanel.direct: «Name:
    dkim._domainkey»), `default` (ISPmanager/opendkim), `mail`, `s1`, `s2`,
    `k1..k3` (rspamd), `google` (Workspace), а в отчёте пишется, сколько
    селекторов искали и что подпись может идти под другим.
  - **Пустой `p=` — отозванный ключ, а не «запись есть».** Подпись с такой
    записью получатель проверить не сможет; частая грабля после «почистили DNS».
  - **Ротация ключей не теряется.** У селектора бывает несколько TXT, и dig
    печатает вторую строку без имени — парсер держит «якорь» на последний
    селектор, иначе боевой ключ пропадал, а первый с пустым `p=` выдавал бы
    «ключ отозван».
  - **SPF ловит ловушки RFC 7208, а не только «есть/нет»:** две SPF-записи
    (§3.6) и больше 10 DNS-запросов (§4.6.4) — это `PermError`, письма
    ОТКЛОНЯЮТСЯ, хотя запись выглядит правильной; `+all` разрешает отправку с
    любого IP; без `all` чужие серверы формально не запрещены; `v=spf` без
    единицы приёмщик не распознаёт вовсе.
  - **PTR спрашивается только по IPv4.** У домена с CNAME на CDN спрашивать `-x`
    нечего, и вместо выдуманного «PTR нет» пишется «не проверен»: мы не знаем
    про него ничего, врать оператору нельзя.
- **Тот же блок — внутри «Досье домена»**, но только у почтовых доменов: у
  чисто веб-домена SPF может не быть намеренно, и ❌ напротив него был бы
  ложным диагнозом. Реализация одна (`mail_auth_lines`) — две копии однажды
  разъехались бы формулировками.
- **Честность про источник записей.** Если зону обслуживает этот же сервер или
  резолвер смотрит в `127.x`/`10.x`/`192.168.x`, `dig` показывает **локальную**
  зону, а не интернет: «SPF есть» при пустой публичной зоне был бы ложью.
  Источник печатается напротив домена вместе с командой сверки извне
  (`dig +short TXT домен @1.1.1.1`).

### Изменено

- **Вердикт домена = худшая из проверок, а не средняя.** В спам письмо кладёт
  одна проваленная проверка, поэтому такие домены идут в начале списка, а
  отсортированы внутри группы алфавитно — иначе список менялся бы от прогона к
  прогону и оператор не узнал бы свой домен.
- **Отсутствие DMARC — замечание, а не провал.** RFC 7489 делает его
  рекомендацией, письма без него продолжают доходить; рисовать за это ❌
  означало бы заставить оператора «чинить» то, что не сломано. Записи без
  обязательного тега `p` приёмник не применяет вовсе — выдумывать вместо него
  «p=none» (мол, режим наблюдения) не стали: DMARC там не работает вообще.
- **Меню не разрослось:** новый отчёт — ровно одна строка в существующей группе
  сводных отчётов (рядом с почтовым инвентарём, как SSL-отчёт стоит рядом с
  доступностью сайтов). Вложенность не добавлена — тест
  `test_main_list_is_still_flat_except_the_mailbox_submenu` сторожит это.

### Тесты

- **+70 тестов (1055 → 1125 по diff'у `--collect-only`)**. Отдельно закрыты:
  перебор селекторов панелей и MTA (`parametrize`), отозванный ключ, якорь при

- **Уборка файлов с паролями переживает кнопку «Стоп».** Добавлен служебный
  канал `ServerChecker.cleanup()` — команды, которым отмена не мешает. Прежний
  `rm` в `finally` шёл через обычный `run()`, падал от `cancel_event` **внутри
  самого cancel-гейта**, и файл с паролем переживал операцию (воспроизведено на
  заглушке транспорта: пароль оставался в хранилище). «Оператор остановил
  работу» не означает «оставь файл с паролем на сервере». Проверка соединения в
  `cleanup()` сохранена, ответ читается настоящий. Долг касался обеих операций:
  env-файла пароля ящика ISPmanager и временного конфига с паролем БД Битрикса
  (`/tmp/.techsupp_dbcheck.cnf`).
- **Файл с паролем получает права 0600 до того, как в нём появляется пароль.**
  Новый `common.prepare_secret_file()` выполняет в одной команде: `rm -f` (по
  фиксированному пути мог лежать чужой файл или symlink — SFTP-запись пошла бы
  по нему и затёрла цель) → `umask 077` → `: > файл` → `chmod 600` → проверка
  записи, и только затем пишет SFTP. Прежний порядок «записали, потом chmod»
  оставлял окно world-readable (проверено: `umask 022` → 644, `umask 077` →
  600; перезапись через SFTP прав не меняет), а отмена между этими шагами
  запирала пароль в открытом для всех файле.
- **Факт удаления проверяется, а не код возврата.** `common.remove_remote_path()`
  после `rm` спрашивает `[ -e путь ]`: `rm -rf` молчит и когда не смог
  (read-only `/tmp`, права), поэтому `rc=0` про успех не говорит ничего.
- **Если убрать секрет не удалось — оператор обязан это увидеть.** В отчёте
  создания/смены пароля ящика появляется `⚠️` с путём для ручного удаления; при
  отмене (когда отчёт не показывается) причина добавляется к тексту исключения.
  В Битриксе причина проброшена во все отчёты, которые дёргают mysql (`SELECT 1`,
  `CURRENT_USER()`, `SHOW GRANTS`, топ-таблицы, перечитывание прав после GRANT)
  отдельным параметром `warn` — в stdout запроса её класть нельзя, парсеры
  приняли бы предупреждение за данные.

## [1.5.0] — 2026-10-21

### Изменено

- **Пароль почтового ящика ISPmanager больше не попадает в `ps` на сервере.**
  Панель берёт его из окружения: `-e 'passwd=$DIAG_MAILBOX_SECRET'`
  `-e 'confirm=$DIAG_MAILBOX_SECRET'` (документация ISPsystem «Mgrctl
  utility», доступно с COREmanager 5.325+). Секрет пишется SFTP во временный
  каталог от `mktemp -d` (0700) с файлом 0600, команда панели его «источает»
  (`.`), после чего каталог удаляется — и внутри составной команды (`rc=$?`
  снимается до `rm`, чтобы очистка не съела код возврата панели), и
  страховкой на стороне программы (при отмене задачи канал закрывается и
  команда до своего `rm` не доходит). В argv на сервере остаётся только имя
  переменной. Причина именно такого канала: наш транспорт — `exec_command`,
  то есть `bash -c '<вся строка>'`, поэтому `export SECRET=...` внутри
  команды светился бы в `ps` ровно как `passwd=...`.
- **Безопасный канал не подменяется тихим фолбэком.** Если `mktemp` не создал
  каталог (read-only `/tmp`, нет coreutils) либо SFTP недоступен, операция
  отменяется с объяснением: «передать пароль безопасно нельзя». Прежний путь
  «пароль аргументом» удалён, а не оставлен запасным — он и был закрываемым
  долгом.
- **В отчёте показывается команда панели**, а не обвязка: `mgrctl -m ispmgr
  email.edit ... -e 'passwd=$DIAG_MAILBOX_SECRET' ...` — её можно повторить
  руками, экспортировав переменную. Ссылки на переменные маскирование не
  трогает (в них нет секрета), настоящие `passwd=`/`confirm=` в тексте ответа
  панели по-прежнему закрываются (`passwd=***`).
- **Предупреждение в отчёте соответствует фактическому каналу**: ISPmanager —
  «в `ps` не светился, файл удалён»; FASTPANEL — `mogwai` принимает пароль
  только аргументом `--password=`, поэтому он был виден в `ps` (ограничение
  CLI панели, говорим прямо).

### Тесты

- `tests/test_discovery.py`: `TestMailboxSecretChannel` (+7) — отказ при
  отсутствии SFTP и при отсутствии `mktemp` (команда панели не уходит ни в

  `HEALTH_CHECK_LIMIT` (25) доменов на прогон; в шапке — «Проверено доменов: N
  из M».
- **Операции с почтовыми ящиками** (подменю «Почтовые ящики ▸» в том же меню —
  три операции в одной строке, чтобы интерфейс не разрастался): создать, сменить
  пароль, удалить. Синтаксис — из официальной документации панелей, а не «по
  памяти»: ISPmanager `mgrctl email.edit` без `elid` создаёт ящик
  (`domainname`/`name`/`plid`/`aliases`/`passwd`/`confirm`/`sok=ok`), смена
  пароля — `email.edit elid=<адрес>`, удаление — `email.delete elid=<адрес>`
  (`elid` ящика — полный адрес); FASTPANEL — `mogwai emails boxes
  create/delete`, удаление только по числовому ID из `boxes list`. Смены пароля
  ящика в CLI FASTPANEL нет — программа говорит об этом прямо, вместо
  выдуманного флага.
- **Безопасность операций**: порядок в каждой операции — поддержка панели (до
  любого запроса к серверу, иначе отказ звучал бы ложным «домен не почтовый») →
  валидация адреса и длины пароля (≥8) → guard (домен обязан быть почтовым этого
  сервера; для создания — что ящика ещё нет, для смены пароля и удаления — что он
  есть) → команда → **подтверждение перечитыванием списка панели**, потому что
  `rc=0` у mgrctl бывает и при неполной операции. Guard различает «ящиков нет»
  (создать первый можно) и «список не получен» (разрушающую операцию не
  разрешаем). Смена пароля и удаление требуют подтверждения, `askyesno` — до
  запроса пароля.
- **Пароль не уезжает в отчёт**: `passwd`/`confirm`/`password` маскируются
  (`passwd=***`), причём маскирование сначала честно разбирает команду `shlex` —
  регэксп съедал только первое слово пароля с пробелом. Адрес приводится к
  нижнему регистру до проверок (панель хранит ящики строчными, `Info@Site.RU`
  создал бы не находящийся дубль), пароль не стрижётся (пробел — валидный
  символ). В `ps` на сервере пароль виден — предупреждение входит в отчёт.

- **«Cron-агенты: установить в crontab»** — дописывает в crontab root ровно ту
  строку, которую рекомендует отчёт (общий литерал `CRON_LINE`): с бэкапом
  crontab через `common.save_crontab_backup`, без дублей (задание ищется по
  полному пути `cron.sh`) и с обязательной проверкой после записи — `rc=0`, но
  строки в crontab нет, считается ошибкой.
- **«Права на базу (SHOW GRANTS)» и «Права на базу: выдать недостающие»** в том
  же меню. Привилегии читаются под учёткой из `dbconn.php` через
  `CURRENT_USER()`, а не по `DBHost`: в `mysql.user` записан хост-паттерн
  (`%`, `%.site.ru`), и `GRANT` на другую строку учётки создал бы вторую учётку,
  ничего не починив. Отчёт сверяет набор с минимумом ядра Битрикса
  (`GRANT_REQUIRED`: DML + DDL + `EXECUTE`/`TRIGGER`/`EVENT`), различает
  `ALL PRIVILEGES` на `*.*` и на базу, выбрасывает `USAGE` (вход есть — делать
  нечего) и отдельно подсвечивает «права остались на другой базе»
  (переименовали/перенесли сайт) и правки по отдельным таблицам. Выдача — с
  подтверждением, одним `GRANT` недостающего на `{DBName}.*` под root-доступом
  (`/root/.my.cnf`), только после `ident_safe()` (имена вне
  `[A-Za-z0-9_$%.-]` в SQL не подставляются) и с обязательным перечитыванием:
  прав после выдачи меньше стало — сообщение честное, а не «готово».
- **«Почта: отправить тестовое письмо»** в том же меню. Адрес спрашивается
  диалогом и валидируется строгой регуляркой ДО любой команды на сервере
  (он попадает в заголовок `To:` и в `grep` по логу). Письмо уходит в
