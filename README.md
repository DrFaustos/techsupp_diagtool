# SSH Диагностика сервера

[![тесты](https://img.shields.io/github/actions/workflow/status/DrFaustos/techsupp_diagtool/tests.yml?branch=main&label=tests)](https://github.com/DrFaustos/techsupp_diagtool/actions/workflows/tests.yml) [![Лицензия: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE) [![Python 3.7+](https://img.shields.io/badge/python-3.7%2B-blue)](https://www.python.org/downloads/)

Многофункциональный инструмент для диагностики и администрирования удалённых серверов через SSH с поддержкой панелей управления **FastPanel** и **ISPmanager** и набором проверок для серверов **1С-Битрикс (BitrixVM)**.

---

## 📋 Возможности

### 🔌 Подключение
- SSH-подключение по паролю или приватному ключу
- Автоматическое определение типа панели управления (FastPanel / ISPmanager)
- Интерактивный терминал с историей команд
- Переключение между серверами без перезапуска программы
- Кнопка "Подключиться" меняется на "Отключиться" (красная) после успешного подключения

### 📊 Диагностика
- **Полная диагностика** – все проверки в одном отчёте
- **Диски и память** – использование дискового пространства, inodes, оперативная память
- **Сеть** – интерфейсы, маршруты, внешний IP, интерфейс по умолчанию, привязка плавающего IP
- **Фаервол** – состояние ufw, iptables, nftables
- **Конфигурация веб-серверов** – проверка синтаксиса nginx и apache
- **Логи сайтов** – поиск ошибок в error-логах (поддержка FastPanel и ISPmanager)
- **Анализ логов доступа** – топ IP, URI, User-Agent с фильтром по дате (поддержка ротационных .gz)
- **Поиск OOM** – поиск событий Out-Of-Memory в системных логах (kern.log, syslog)

### 🔎 Дополнительные проверки
- **SSL-сертификат** – срок действия, эмитент, SAN (openssl)
  - **Срок — точным остатком и в тех же словах, что в хостинг-отчётах**
    (`❌ SSL ИСТЁК 5 дн. назад`, `⚠️ SSL осталось 3 дн.`, `✅ SSL осталось 87 дн.`).
    Прежняя подпись строилась строкой `'VALID' in out_days` из отдельной команды
    `openssl x509 -checkend 0`, а её код возврата был выброшен: `timeout 10`,
    отсутствие openssl или разорванное соединение дают пустой вывод, «VALID» в нём
    нет — и отчёт печатал «❌ Сертификат ИСТЁК». Оператор ехал перевыпускать
    сертификат, которого на этом порту, возможно, и нет. Второе враньё той же
    команды: `-checkend 0` отвечает только «истёк ли СЕЙЧАС», поэтому сертификат,
    умирающий завтра, был «✅ действителен».
  - **Сетевых проб стало меньше, а не больше**: `notAfter` уже лежит в первом
    ответе, поэтому остаток добирается локальной `date` на сервере (дни считаются
    там: дата машины оператора к выпуску сертификата отношения не имеет), а вторая
    проба удалена совсем. Не удалось посчитать срок — `❓ срок действия не
    определён`, ни зелёного, ни красного: любое из них было бы догадкой.
- **WHOIS** – регистратор, даты регистрации/истечения, NS
  - **Пустой ответ разбирается по коду возврата и stderr, а не сваливается в
    «whois не установлен или домен не найден».** Прежний код принимал `rc` и не
    использовал его, а `2>/dev/null` глушил ровно ту строку, где написана причина.
    Измерено живьём на машине без утилиты: `rc=127` и stderr
    `timeout: failed to run command 'whois': No such file or directory`; семантика
    `timeout` тоже замерена, а не взята из мануала: 124 — убит по таймауту, 127 —
    бинарника нет, 1 — команда упала, 0 — успех. Теперь четыре разных диагноза:
    `❌ whois на сервере не установлен (rc=127) … apt install whois`,
    `⚠️ whois не успел ответить за 15 сек (rc=124) … проверьте исходящий порт 43`,
    `⚠️ Запрос whois не выполнен (rc=N)` плюс строка `Ответ системы:` из stderr,
    `❓ Ответ реестра пуст без ошибки (rc=0) — состояние не проверено`. Ни один из
    них не называется вердиктом про домен: права говорить о домене у пустого
    ответа нет.
  - **«Домена нет» произносит реестр, а не программа.** Такой ответ — НЕ пустой.
    Живые запросы к реестрам через TCP/43 (утилиты `whois` на машине как раз не
    было — об этом и правка) дали `No match for "…COM".` (Verisign),
    `No entries found for the selected source(s).` (TcI и RU-CENTER),
    `Domain not found.` (nic.me), `This domain name has not been registered.`
    (Nominet). Отчёт цитирует строку реестра, чтобы оператор видел, чем именно
    подтверждён ответ. Служебное `NOT FOUND` внутри записи зарегистрированного
    домена (например, в contact-строке) ложного «свободен» не даёт: вердикт
    возможен только когда в выводе нет ни одного поля записи.
  - **Цена не выросла**: та же одна команда, `stderr` просто перестаёт выбрасываться.
- **Сканирование портов** – слушающие (ss/netstat) + типовые порты
  - **Итог проб — четыре разных диагноза, а не одна фраза «не ответил».** Прежний
    код выбрасывал код возврата всех 18 проб (`out2, _, _ = checker.run(...)`), а
    пустой вывод у противоположных ситуаций одинаковый. Проверено живьём:
    `connection refused` — это rc=1 за 4 мс (хост жив, он присылает RST: служба не
    слушает), недоступный или фильтруемый хост — rc=124 за 2002 мс (пакеты молча
    дрейфуют). Теперь: `❌ Порты закрыты: 18 из 18 … отклонены (RST)` (чинить
    службы), `⚠️ Порты не видно: 18 из 18 молчат … firewall / cloud security
    group / ваш IP` (службы могут работать), `⚠️ Ответили не на всё: из 18 молчат
    15` (смешанный ответ — про «закрыто» говорить нельзя), `❓ Состояние проб
    неизвестно` (команда не выполнилась — это «не проверено», а не «порты
    закрыты»). Оператору, которому фильтруют путь, прежняя фраза отправляла
    перезагружать живой сервер.
  - **Связка «слушает тут, молчит снаружи»** показывается отдельной строкой `ℹ️`:
    если `ss` на сервере видит порт, а проба снаружи на него не получила ответа —
    это фильтрация пути, а не упавшая служба. Данные уже лежат в том же прогоне —
    ни одного нового сетевого запроса, SSH-команд как было две, так и осталось.
  - **Хост больше не подставляется в команду неэкранированным.** Вскрыто живым
    прогоном: значение вида `127.0.0.1; echo INJECTED` реально выполнялся (rc=0 —
    то есть 18 ложных «порт открыт»). Кавычки внутрь пути `/dev/tcp/...` ставить
    нельзя (проверено: проба ломается), поэтому адрес уходит отдельным словом и
    попадает в путь позиционным параметром.
- **Grep логов** – массовый поиск по access/error-логам (5xx, 404 и др.)
  - **«Совпадений нет» звучит только про прочитанный лог.** Прежняя строка
    `out, _, _ = checker.run(f"{base} 2>/dev/null | grep … | tail -n N")`
    сваливала в неё шесть разных ситуаций. Код возврата `grep` различает
    1 («совпадений правда нет») и 2 («файл не открылся») — замерено живьём, но
    забрать его было нельзя: rc конвейера равен rc последней команды, то есть
    `tail`, которая всегда 0 (замер: `grep_rc=1 rdr_rc=1 tail_rc=0`). Теперь
    состояния разделены: `❌ файл не читается: не хватает прав (логи часто
    640 root:adm)`, `❌ файл исчез между поиском и чтением — так делает
    logrotate`, `на сервере нет zcat`, `❌ шаблон не разобран`, `❓ сервер не
    вернул ответа`. Ни одно из них не называется вердиктом про содержимое лога.
  - **Шаблон проверяется до чтения файла.** Regex вводит оператор, а опечатка
    (`5[0-9`) роняет `grep` с rc=2 и пустым выводом — раньше это читалось как
    «проблем в логе нет». Различение снято живьём (bash и dash):
    `grep -E "$P" /dev/null` даёт rc=1 для валидного и rc=2 для разбитого
    шаблона — именно без конвейера; проверка вида `printf '' | grep -E "$P"`
    битый шаблон НЕ отличает (у grep'а на пустом входе rc=1 по любой причине).
  - **Масштаб считается по всем совпадениям, а не по показанным.** `tail -n`
    резал вывод, а «Всего строк» считалось по остатку: 4 совпадения при лимите 2
    давали отчёт «Всего строк: 2». Плюс один и тот же файл попадал в поиск
    дважды (маски access и error пересекаются) — при 2 совпадениях отчёт писал
    «6». Итог считается awk-буфером за один проход; при контексте (`-C`)
    совпадения отличают от строк контекста по префиксу `-n`, иначе `-C` завышал
    бы итог. Если часть логов не прочитана, «совпадений нет» не печатается вовсе:
    `⚠️ Прочитано 1 из 2 файлов … 1 файл мы не видели`.
  - **Различение — POSIX-ветками, а не `${PIPESTATUS}`**: под `dash` (обычный
    `/bin/sh` в Debian/Ubuntu) последний даёт «Bad substitution» — проверено
    живьём. Команда продукта прогнана через `bash` и `dash` на реальных файлах
    во всех десяти состояниях.
  - **Цена не выросла**: одна SSH-команда на файл (состояние + точный итог +
    хвост одним прогоном), `stderr` читателя не глушится — `gzip: not in gzip
    format` доходит оператору вместо ложного «совпадений нет» по всем архивам.
  - **Пустота ПОИСКА логов тоже объясняется, а не подписывается «не найдено».**
    Шаг выше по стеку врал так же: `ls -1 {glob} 2>/dev/null | head -20` с
    выброшенным кодом возврата. Замерено живьём: честный `rc` у `ls` **не
    различает** причины пустоты — «файлов нет», «каталога нет» и «нет прав» дают
    один `rc=2`; различает только ответ системы (`Permission denied` против
    `No such file or directory`). И `[ ! -d ]` физически не отличает «каталога
    нет» от «его не видно, потому что закрыт родительский каталог» — отвечает
    «нет» в обоих случаях, поэтому приоритет отдан stderr, а не проверке `[ -d ]`.
    Теперь у каждой причины своя строка: `⚠️ Каталог … не читается под этим
    пользователем: нет прав на каталог (нужны r-x) … это «мы не увидели», а не
    «файлов нет»`, `⚠️ Каталога … нет на сервере — проверьте раскладку и тип
    панели`, `⚠️ Путь … недоступен — ответ системы: «ls: … Permission denied» …
    состояние не проверено`, `⚠️ Показаны первые 5 файлов из 30: остальные в этом
    отчёте не участвовали`. Прежние `head -20` резали список молча, а
    предупреждение о срезке потребители выбрасывали фильтром.
  - **«Логи для домена не найдены» звучит только когда каталоги действительно
    просмотрены и пусты.** Если сервер не подтвердил просмотр ни одного каталога
    (обрыв, отмена) — `❓ состояние не проверено`, а не «логов нет». То же в
    «Анализе доступа»: вместо `❌ Не найден access-лог` оператор получает причину
    (права / раскладка / неподтверждённый ответ).
  - **Цена та же**: одна SSH-команда на поисковый паттерн — состояние каталога,
    список и честное число файлов снимаются одним прогоном.
  - **ЧТЕНИЕ файла тоже отвечает состоянием, а не `None`.** Шагом ниже стояли
    `cat {путь} 2>/dev/null` с `if rc != 0: return None` и
    `ls -1 {паттерн} 2>/dev/null | head -1` с `return None`. Замерено живьём
    (uid=1000): `rc=1` одинаково дают «нет прав» (`cat: …: Permission denied`) и
    «нет файла» (`cat: …: No such file or directory`), а `rc=0` — и прочитанный
    файл, и прочитанный **пустой**. То есть «я не имел права читать», «файла
    нет», «это каталог» и «файл пустой» были одним значением, а вызывающий код
    глушил его в `or ''`. Теперь у каждого состояния своя строка:
    `⚠️ Лог … не просмотрен: не читается под этим пользователем: нет прав на
    файл`, `файла нет на сервере — проверьте раскладку и тип панели`,
    `по этому пути каталог, а не файл`, `состояние не проверено: сервер не
    подтвердил чтение`.
  - **Снова спас приоритет ответа системы, а не проверки `[ ]`.** У файла внутри
    закрытого каталога `[ ! -e ]` отвечает «нет файла» — `stat` невозможен без
    `x` на каталог, — тогда как `cat` в stderr говорит `Permission denied`.
    Поэтому читатель вызывается **всегда**, а python при `Permission denied`
    перекрывает `missing` → `unreadable` (тот же закон, что спас в 1.20.0 на
    уровне каталога, но уровнем ниже; поймано живым прогоном).
  - **Нечитаемый лог больше не называется «чисто».** `Ошибок (по ключевым словам)
    в логах сайтов не обнаружено` печаталось и когда ни один лог не был открыт
    (права `0600 root:adm`): пропуск шёл молча. Теперь — `❌ Часть логов сайтов
    не просмотрена (прочитано файлов: 0)` со списком файлов и причин. Так же в
    «Анализе посещений»: вместо `За указанный период записей не найдено` при
    закрытом access-логе — причина; строка `Обработано файлов: N` считает
    **прочитанные**, а не найденные.
  - **Битый `.gz` больше не «пустой архив».** `zcat … 2>/dev/null` терял
    `gzip: …: not in gzip format`, и битый архив для отчёта означал «записей
    нет». Ответ системы цитируется: `читатель (zcat) сообщил об ошибке: «gzip:
    …» — вывод неполон`.
  - **«Домены не определены» различает «панель не ответила» и «конфигов нет».**
    `mgrctl … 2>/dev/null` и `ls -1 {каталог vhost'ов} 2>/dev/null | head -10`
    враньём закрывали и отказ панели, и отсутствие прав, и срезку списка: на 40
    конфигах отчёт «смотрел» десять и называл это полным списком доменов.
  - **Цена не выросла**: одна SSH-команда на чтение файла (состояние и содержимое
    одним прогоном, `.gz` через тот же `zcat`), поиски доменов — по одному
    запросу на паттерн, как раньше. Служебные `RFSTATE`/`FFDIR`/`FFCOUNT`
    оператору не показываются.
  - **Домены из конфигов: «нет прав» больше не выдаётся за «доменов нет».**
    Прежний вид (`common.get_domain_from_config`):

        grep -h 'server_name' … 2>/dev/null | sed … | tr … | grep -v …

    Терялись ТРИ вещи сразу. `2>/dev/null` глушил единственную строку, где
    написано ПОЧЕМУ пусто. Пайп **забирал код возврата**: конвейер отдаёт rc
    последней команды (`grep -v`), а тот сообщает лишь «фильтр что-то пропустил»
    — про права пайп не говорит НИКОГДА. Вывод был уже извлечёнными именами,
    поэтому тестовый двойник описывал ответ, которого `grep` не выдаёт, и чинить
    пайп под зелёными тестами было нельзя. Замер живьём (uid=1000), ОДНА команда
    `grep -h 'server_name' ПУТЬ 2>&1`, rc принадлежит grep'у:

        читаемый, домены есть      rc=0  server_name example.com www.example.com;
        прочитан, server_name нет  rc=1  (пусто)
        ЗАКРЫТ 0000                rc=2  grep: …: Permission denied
        ОТСУТСТВУЕТ                rc=2  grep: …: No such file or directory
        КАТАЛОГ                    rc=2  grep: …: Is a directory

    Прежняя команда на трёх последних состояниях давала ровно тот же `[]`, что и
    на честном «доменов нет», — а лечения противоположные: поднимать права против
    менять раскладку панели. Именно этот список доменов кормит все отчёты.
  - **Парсер `server_name` переехал на python и перестал выдумывать домены.**
    Прежний `sed` (жадный `.*server_name`) на настоящих файлах давал:
    `#    server_name uhatil.tld;` → домен `uhatil.tld` (комментарий),
    `server_names_hash_bucket_size 128.0;` → домен `128.0` (это не директива
    `server_name`), а `server_name hodovyj.tld; # server_name ljevoj.tld;`
    терял настоящий домен и возвращал выдуманный. По таким именам отчёт идёт
    читать `/var/log/nginx/128.0.error.log`.
  - **Одно признание на основание, а не на файл.** Десять конфигов с правами
    `0000` сразу после первой правки дали десять одинаковых строк — признание,
    которого десять, оператор перестаёт читать. Теперь сводка одна и она называет
    масштаб: `⚠️ Домены по 10 файлам (…site0.conf и ещё 9): нет прав на файл
    конфига …`. Разные же ответы системы («memory exhausted» против «input file
    is also the output») не сливаются: это разные основания, и каждый цитируется.
  - **Цена не выросла, а упала**: тот же прогон — 24 → 12 SSH-команд (найденный
    конфиг больше не читается заново под каждым паттерном `DOMAIN_PATHS`),
    grep-чтений 18 → 6, слепых `2>/dev/null` в отправленных командах 18 → 0.
- **Поиск OOM объясняет, почему он был неполным.** Прежний вид:
  `zgrep … /var/log/kern.log* /var/log/syslog* 2>/dev/null`, код возврата
  принимался и выбрасывался, а `if not out.strip()` означал
  `«OOM-событий в логах не найдено»`. Пустой вывод тут дают пять разных вещей, и
  все они были подписаны одинаково: файл лога не читается под этим пользователем
  (обычно `0640 root:adm`); `/var/log/kern.log*` и `/var/log/syslog*` нет вовсе —
  ядро пишет в журнал systemd, что норма для Ubuntu 22.04+/Debian 12+;
  ротированный `.gz` битый; `zgrep` не установлен; ответ сервера оборвался.
  Теперь вместо ложного «событий нет» — `❌ Поиск OOM выполнен не полностью:` со
  списком файлов и причин (`journalctl -k --grep=oom` подсказкой для systemd-
  хостов), а «не найдено» звучит только когда хотя бы один лог прочитан и ни
  один не отвалился.
  - **Битый архив ловится отдельной проверкой.** Замерено живьём: `zgrep` на
    файле, который не является gzip, молчит с кодом возврата 1 — ровно как на
    прочитанном логе без совпадений. Поэтому в ту же команду добавлен `gzip -t`,
    а его stderr не заглушён: `Файл … не просмотрен: gzip не смог открыть архив
    (битый или недокачанный лог) — содержимое этого файла в отчёте не
    участвовало, а zgrep об этом молчит`.
  - **Список файлов один.** Пути логов были записаны дважды — в команде и в
    строке `Файлы: …`; теперь их задаёт `OOM_GLOBS`, из которого строятся и то,
    и другое (разъехавшийся дубль обещает «искали в одних, отчитались по
    другим»).
  - **Цена та же**: одна SSH-команда на весь поиск — состояние каждого файла,
    проверка архивов и сам `zgrep` снимаются одним прогоном; служебные
    `OOMSTAT`/`OOMUNREAD`/`OOMBADGZ`/`OOMEND` оператору не показываются.
- **Редактор конфигов больше не путает «не прочитал» с «файл пустой» и не портит
  файл при сохранении.** Прежний `read_file`: `cat … 2>/dev/null`, а при `rc != 0`
  — `«❌ Ошибка чтения файла (rc=1): {err}»`. Сообщение обещало причину ПОСЛЕ
  двоеточия, а та же команда её же и заглушала: файл с правами `0600`,
  отсутствующий файл, файл внутри каталога без прав и сам каталог давали одну и ту
  же строку с ПУСТЫМ хвостом (замер живьём — четыре одинаковых ответа).
  `gui_admin` вставлял возвращённое в окно редактора как содержимое, и «Сохранить»
  (сторожа там не было; в файловом менеджере такой сторож есть) записывало текст
  ошибки на сервер по пути конфига. Теперь отказ начинается с ❌, называет
  состояние словами (нет прав / файла нет / это каталог / состояние не проверено)
  и в редактор не попадает: прежнее содержимое остаётся в окне, причина — в диалоге.
  - **Содержимое возвращается байт в байт.** Разбор ответа собирал тело как
    `''.join(splitlines()[1:])` через перевод строки, а `splitlines()` отбрасывает
    завершающий перевод строки и режет по `\r\n`, выбрасывая сам `\r` — замер: 4 из
    6 форматов возвращались укороченными (`worker 4;` + перевод строки → `worker 4;`).
    Для лога это безразлично, для конфига — тихая порча данных.
  - **Сохранение не сдвигает хвост файла.** `get(1.0, END)` добавляет к тексту
    окна РОВНО один перевод строки: в редакторе админки его не снимали вовсе
    («открыл → Сохранить» дописывало в конфиг пустую строку), в файловом менеджере
    срезали `rstrip('\n')`, то есть все хвостовые переводы разом (файл с пустой
    строкой в конце уходил на сервер без неё). Снимается ровно один перевод,
    добавленный виджетом.
  - **Отказ записи больше не «Успех».** `write_file` при неудачном SFTP
    возвращает отчёт, начинающийся с ❌, а редакторы рапортовали «Файл сохранён»
    и «Готово» на любой результат — то есть врали о записанном конфиге.
- **Отмена задач** – кнопка «✖ Отменить» прерывает долгую операцию
- **Прогресс этапов** – индикатор 1/N…N/N при полной диагностике
- **Профили серверов** – сохранение/загрузка реквизитов в JSON (~/.techsupp_diagtool_profiles.json)

### 🔧 Администрирование
- **Редактор конфигов** – просмотр и редактирование конфигурационных файлов (nginx, apache, php, mysql) с созданием резервных копий
  - **Пустой список обязан называть причину, а не «файлы не найдены».** Здесь
    вранье стоило дороже молчания: `ls -d ПУТЬ` печатает сам путь, а
    `echo exists` — второй строкой, поэтому прежнее сравнение ответа с `exists`
    не истина никогда. Замер живьём (`uid=1000`, `/bin/bash`): и одиночный
    конфиг, и каталог с файлами, и пустой, и закрытый каталог давали False — то
    есть редактор возвращал пустой список на ЛЮБОМ сервере и рапортовал «не
    найдены» там, где все конфиги есть. Теперь поиск ведёт примитив
    состояния каталога (одна команда на путь вместо двух глухих), а диалог
    различает «файлов нет» (информация) и «не смогли посмотреть» (нужны права)
    — у этих двух ответов разные действия оператора.
  - **Каталог не предлагается как файл.** Пустой прочитанный каталог раньше
    попадал в список «конфигов», и редактор открывал его как файл. Пустой
    **прочитанный** каталог жалобы не даёт: «файлов нет» — честный ответ, шум
    обесценил бы настоящие предупреждения.
- **Файловый менеджер** – навигация по каталогам по SFTP, правка текстовых файлов, скачать/загрузить
- **Замена IPv4** – замена IP-адреса во всех .conf-файлах в /etc
- **Замена IPv6** – замена IPv6-адреса во всех файлах в /etc (⚠️ включая бинарные; перед заменой создаётся бэкап /etc)
- **Перезапуск служб** – перезапуск nginx, mysql, apache

### 🌐 Инвентарь хостинга
Меню «🌐 Хостинг ▾» видно при **любом** подключении — работает и на сервере без
панели (сайты по vhost'ам, почта по картам postfix и dovecot):
- **Полный инвентарь сервера** — сайты + почта + DNS-зоны одним отчётом
- **Сайты: список и доступность** — панельный источник (`mgrctl webdomain` /
  `mogwai sites list`) приоритетнее разбора конфигов: владельцем, docroot, версия
  PHP и источник каждой записи показаны явно; у каждого сайта проверяются
  http/https-коды и остаток SSL (не больше 25 внешних проб на прогон).
  Над списком печатается сводка «Проверено доступности: 25 из 30: HTTPS 2xx/3xx —
  22, только HTTP — 2, молчит — 1» и отдельной строкой «SSL: истёк — 1, истекает
  < 30 дн. — 3»: при 25 доменах оператор обязан узнать масштаб беды, а не
  досчитывать иконки глазами. Считается **состоянием** сайта (та же функция, что
  возвращает иконку строки), а не поиском «❌» в готовом тексте: в строке домена
  ДВЕ иконки — доступности и сертификата, и подсчёт по символу записал бы
  мёртвый сертификат как упавший сайт. Число непроверенных доменов называет
  знаменатель «25 из 30» — отдельной строки о них нет намеренно (то же решение,
  что отказ от сводки «расхождений нет» в SPF-отчёте). Проба снимается **один**
  раз и кормит и сводку, и список: второй вызов означал бы ещё 25 хендшейков
  - **«Сайты не обнаружены» больше не означает «мы не смогли их увидеть».**
    Замер живьём (uid=1000, настоящие файлы против `discovery`): закрытый
    vhost (0600 root), закрытый каталог vhost'ов, отсутствующий каталог и
    реально пустой конфиг давали ОДИН вывод — пустой список и строку «Сайты не
    обнаружены». Различение уже считалось (`find_files` — 1.20.0,
    `read_file_info` — 1.21.0), но здесь выбрасывалось: ⚠️-строки фильтром
    «это не путь», а причина чтения — гашением `None` в `or ''`. Теперь
    `discover_sites_info` отдаёт и причины, а оба отчёта по инвентарю печатают
    их — в том числе когда сайты нашлись: «Найдено сайтов: 3» при закрытом
    каталоге, где лежат ещё двадцать, — тоже недостоверный итог. Пустой
    ПРОЧИТАННЫЙ конфиг жалобы не даёт: «пусто» — честный ответ, шум обесценил
    бы настоящие предупреждения.
- **Почта: домены, ящики, очередь** — домены из панели, `postfix virtual`,
  `dovecot users` и `main.cf` с указанием источника; очередь `mailq`; статусы
  postfix/dovecot/opendkim/rspamd одной командой; рядом — разбор последних
  отказов доставки (см. «Доставка писем по логу»). Правая часть строки карты —
  адрес доставки на чужой сервер — почтовым доменом этого сервера не считается
  - **Число «Почтовых доменов: N» обязано быть достоверным.** Замер живьём
    (uid=1000, настоящие файлы против `discovery`): контроль давал 3 домена, а
    закрытая карта (0600 root), пустая карта и отсутствующая карта давали
    **побайтово одинаковый** отчёт «Почтовых доменов: 2». Здесь ложь опаснее,
    чем в инвентаре сайтов: отчёт печатает число, то есть утверждает, а не
    молчит. Причина — `if content:` после `read_file_content`, где `None`
    («не прочитали») и `''` («карта пустая») сливались в одно «доменов нет».
  - **Три состояния разведены, и разведены по-разному для отчёта и для
    операции.** «Не удалось прочесть» (права, обрыв ответа, каталог вместо
    файла) — блокирует: по такому источнику нельзя ни писать «доменов нет», ни
    разрешать/запрещать операцию. «Файла нет» — НЕ блокирует: на него смотрели,
    его нет, на сервере без postfix это норма, и вывод «домена из него нет» по
    нему законен. Пустой **прочитанный** файл — честный ответ без жалобы.
  - **Опасная часть прежней лжи — операция, а не отчёт.** Тот же инвентарь
    стоит шлюзом к созданию ящика (`mailbox_guard`) и при недоступной карте
    отказывал текстом «Сначала добавьте домен в панель» — то есть отправлял
    оператора менять конфигурацию почтового сервера по признаку «мы не
    посмотрели». Отказ сохранён (защиту не ослабляем), но теперь названа
    причина и что с ней делать. Корректный образец лежал рядом, в том же файле:
    `known_mailbox_addresses` возвращает `(множество, ok)` и прямо пишет, что по
    неполученному списку нельзя ни разрешать, ни запрещать.
- **Почта: SPF/DKIM/DMARC/PTR** — ответ на тикет «почта работает, а письма уходят в
  спам»: причина обычно в DNS, а не в postfix. Проверка не использует синтаксис панелей —
  те же `dig`, что и в досье домена: на домен 5 запросов (A, TXT, `_dmarc`, цикл по
  селекторам DKIM, PTR), не больше 25 доменов на прогон. Вердикт домена — **худшая** из
  проверок: в спам письмо кладёт одна проваленная проверка, а не средняя арифметическая,
  поэтому такие домены идут в начале списка.
  - **«Не прочитали `/etc/resolv.conf» — не то же, что «резолвер внешний».**
    Основание писать «dig показывает локальную зону, а не интернет» ровно два:
    прочитанный resolv.conf с `nameserver` на 127.x/::1/10.x/192.168.x и
    найденная локальная зона. Замер живьём (uid=1000, `/bin/bash`, настоящие
    файлы): закрытый `0000` resolv.conf и прочитанный `nameserver 1.1.1.1`
    давали одинаковую пустую пометку — отчёт молча подразумевал «видно
    интернет», файла не касаясь. Теперь признание печатается один раз на прогон
    и до списка доменов (пометка про резолвер — про сервер, а не про домен).
  - **Незнание намеренно не подмешано в пометку о локальной зоне.** Она —
    условие внешней сверки: непустая строка означает «показано локальное
    содержимое» и запускает 5 внешних `dig` на каждый домен. «Файл не читан»
    локальность не доказывает, поэтому идёт отдельным каналом
    (`resolver_view_info` отдаёт `(note, unknown)`): иначе ложное «возможно,
    локально» заставило бы платить запросами там, где беда не доказана.
    Пустой **прочитанный** resolv.conf жалобы не даёт: «nameserver нет» — ответ.
  - **DKIM-селекторы перебираются списком**, а не одним именем: запись живёт в
    `<selector>._domainkey.<domain>`, и получатель ищет её по тегу `s=` из заголовка
    `DKIM-Signature`. В списке `dkim` (FASTPANEL, kb.fastpanel.direct), `default`
    (ISPmanager/opendkim), `mail`/`s1`/`s2`/`k1..k3` (rspamd), `google` (Workspace) —
    «DKIM нет» честно только при переборе, и в отчёте написано, сколько селекторов
    искали. Пустой `p=` — отозванный ключ, а не «запись есть»: подпись с ним проверить
    нельзя. При ротации ключей у селектора несколько TXT-строк — боевой ключ не теряется.
  - **SPF** ловит ловушки RFC 7208, а не только «есть/нет»: две SPF-записи и больше 10
    DNS-запросов — это `PermError` (письма ОТКЛОНЯЮТСЯ, хотя запись выглядит правильной),
    `+all` разрешает отправку с любого IP, отсутствие `all` формально не запрещает чужие
    серверы.
  - **DMARC** без записи — замечание, а не беда (RFC 7489 — рекомендация, письма ходят);
    запись без обязательного тега `p` приёмник не применяет вовсе, и выдумывать вместо
    него «p=none» программа не станет.
  - **PTR** спрашивается только когда у домена есть IPv4 (спрашивать `-x` у CNAME
    нечего), а без адреса пишется «не проверен», а не «не пройден».
  - **Строка «→» — что именно вставить в DNS.** Отвечать «где чинить» мало:
    оператору нужен ответ «что вставить». Подсказки расходятся по машинночитаемому
    коду беды (`reason`), а не по тексту отчёта: формулировки правятся ради
    читаемости, и подсказка, привязанная к фразе, отвалилась бы молча и показала
    бы оператору неверную запись. SPF собирается из фактов этого же прогона
    (A-запись → `ip4:`, иначе `a`) и всегда `~all`, а не `-all`: жёсткий запрет
    ломает доставку через CRM и рассылки, которых мы ещё не знаем. Основание
    записи распечатывается рядом и обязано описывать ровно тот механизм, что
    попал в строку: при отсутствующей или **приватной** A-записи (`10.x`,
    `192.168.x`) предлагать `ip4:10.0.0.5` — выдать заведомо мёртвую запись
    (приёмник смотрит на адрес TCP-сессии), поэтому там `a` с объяснением.
    DMARC начинается с `p=none` + `rua` на сам домен: поднять сразу `reject`
    без сводок — дать приёмнику право убивать письма, о которых ничего не
    известно, а `rua` на чужой домен приёмник верифицирует отдельно и сводки не
    приходили бы никогда. **DKIM не генерируется никогда**: публичная TXT
    выводится из приватного ключа, который живёт на сервере, — вместо выдуманной
    «готовой записи» (её приёмник отверг бы, а оператор решил бы, что «всё
    сделали») подсказка говорит, где взять настоящую: панель либо ключи MTA
    (`/etc/rspamd/dkim`, `/etc/opendkim/keys/<домен>/`), брать `.txt`, никогда
    не `.key`. У настроенного домена подсказок нет вообще — пустой блок честнее
    советов про то, что уже работает.
  - **Строки «🌐» — программа сама смотрит из интернета.** Предупредить «у вас
    локальная зона, сверьте вручную» мало: оператор получает «SPF ✅» и
    останавливается, а публичная зона может быть пустой. Поэтому отчёт повторяет
    те же запросы к публичному резолверу и печатает расхождения строками
    «🌐 … извне». Вердикт, иконки шапки и подсказки «что вставить» считаются по
    **публичной** картине — письмо судит приёмник, который видит DNS интернета,
    а не файл нашей зоны. Локальные строки при этом остаются напечатаны: по ним
    ищут, где именно зона разошлась. Разобранные внешние ответы проходят **теми
    же парсерами**, что и локальные, — второй набор правил однажды начал бы
    спорить с первым, и оператор читал бы это как «отчёт врёт».
  - **Масштаб беды — в первой строке, до списка доменов.** При 25 доменах
    «несколько доменов с 🌐» оператору ничего не говорит: нужно «🌐 Расходится с
    публичной зоной: 4 (сверено доменов: 25)» — это ответ на решение «править
    зону централизованно» либо «разбираться по доменам». Счётчик ведёт
    **состояние сверки каждого домена**, а не поиск символа «🌐» в готовом
    тексте: этот символ печатается в трёх несходных случаях — «зона разошлась»,
    «публичные записи совпали», «сверить не удалось», — и подсчёт по подстроке
    дал бы число, которого нет (оператор прочитал бы «расходится: 7» там, где
    семь доменов просто не удалось проверить). Число даётся со знаменателем —
    «4 (сверено доменов: 25)»: четыре расхождения при одном сверенном домене и
    при двадцати пяти — разный объём работ. Считаются **только проверенные**
    домены: те, что остались за `HEALTH_CHECK_LIMIT`, в счётчик не попадают.
  - **Совпавшее не дублируется, непроверенное не прячется.** Отдельной строки
    «расхождений нет» нет намеренно: в теле каждого домена уже напечатано
    «🌐 сверка через 1.1.1.1: публичные записи совпадают» — там назван даже
    резолвер, а повтор оператор читает как невнимательность и перестаёт доверять
    выводу. «Не удалось сверить» — отдельная строка с собственным числом: 2 беды
    и 20 «не видно» — это разные решения (чинить зону и поднимать резолвер), и
    складывать их нельзя. Если сверки не было ни у кого (зоны внешние, смотреть
    нечего), сводка молчит: «расхождений нет» означало бы «мы проверили и всё
    чисто», чего мы не проверяли.
  - **Сверка платит только там, где ложь возможна**: ещё 5 запросов на домен
    идут лишь у доменов с локальной зоной или локальным резолвером (условие и
    текст пометки берутся из одной функции — иначе «где сверять» и «где написано,
    что сверять надо» разъехались бы), а жив ли резолвер спрашивается **один** раз
    на прогон. Probe обязан спрашивать заведомо живое имя: домен с пустой зоной
    отвечает так же пусто, как недоступный DNS, и по запросу к самому домену «жив
    ли DNS» не отличить.
  - **Резолвер задаётся строго через `@server`.** Живой прогон показал, что
    positional-форма (`dig A name 1.1.1.1`) адрес сервером не считает: запрос
    уходил на местный резолвер и отвечал за 0.0 с даже при заведомо мёртвом IP.
    Оставить её — значит выдать локальную зону с подписью «из интернета», ровно
    ту ложь, ради исправления которой сверка и пишется.
  - **«Не получили ответ» — это не «записей нет».** При недоступном резолвере
    `dig` возвращает rc=9 и пишет `;; communications error` в **stdout**
    (`2>/dev/null` от этого не спасает), а честный пустой ответ — это rc=0 и
    молчание. Решение принимает rc, напечатанный самой командой; `;;`-строки
    отсекаются, иначе текст ошибки ушёл бы в парсер TXT как значение записи. У
    внешнего цикла DKIM rc — **флаг по всему циклу**: код последней команды
    молчит о предыдущих, и одна таймаутная итерация выглядела бы как «извне
    записей нет». У внешнего PTR собственный признак ответа (он зависит от
    внешней A и идёт пятым): таймаут по `-x` обязан дать «не получен», а не
    «обратной записи нет» — это то же враньё, только в обратную сторону.
  - **Непроверенное не имеет права выглядеть как «в порядке».** Если сверка
    домену была нужна, но не состоялась (резолвер жив, а по домену не ответил —
    или живых публичных резолверов нет вовсе), домен помечается `[не сверено]` и
    получает warn вместо ok, а рядом печатается команда ручной сверки. Понижения
    строгости нет: bad остаётся bad — поднять можно только ok.
  - Отдельная честность: если DNS-зону обслуживает этот же сервер или резолвер
    смотрит в `127.x`/`10.x`/`192.168.x`, `dig` показывает **локальную** зону, а
    не интернет. «SPF есть» при пустой публичной зоне был бы ложным диагнозом,
    поэтому источник записей печатается напротив домена, а команда ручной сверки
    (`dig +short TXT домен @1.1.1.1`) даётся только там, где свериться самим не
    удалось.
- **Доставка писем по логу** — `mailq` отвечает «сколько писем стоит», но не
  отвечает «почему». Отчёт разбирает строки доставки postfix (`to=`, `dsn=`,
  `status=`) и печатает отказы с причиной: «спам или блокировка репутации»,
  «DNS домена получателя», «нет соединения с портом 25», «отказ в релее»,
  «адресата нет», «временный отказ» — и домены получателей, которым бьёт.
  - **Причина берётся из текста приёмника, а не из догадки.** Иглы групп —
    дословные фразы в скобках после `status=` (Gmail прямо пишет
    `unauthenticated mail was rejected, please learn about SPF` — то есть
    причину отказа в письме видно заодно с проваленным SPF). Распознать
    произвольную строку невозможно — в этом случае печатается её оригинал, а
    не выдуманная причина: оператор понесёт клиенту именно то, что напечатал
    приёмник.
    - **Причину ищут до конца строки.** Прежний жадный шаблон «между первой и
      последней скобкой» терял её целиком на живом сервере: postfix дробит
      многострочный SMTP-ответ (`550-…` несколькими записями), а rsyslog режет
      строку по `$MaxLine` — закрывающей скобки в хвосте нет. Потерянная
      причина — потерянный диагноз, и ровно кейс «Gmail отбил за SPF» остался
      бы без подсказки.
  - **Читается ОДИН почтовый лог на прогон, и не только `maillog`.** Выбор
    файла (`/var/log/maillog` → `/var/log/mail.log` → `journalctl -u postfix`)
    делает одна функция на весь проект: у нас уже были парные реализации, а
    здесь расхождение выглядело бы как «в одном отчёте лог есть, в другом —
    логов нет». Раньше читался только `maillog`, и на Debian отчёт о почте был
    слеп — об этом честно писал наш собственный текст («лог может писаться в
    `/var/log/mail.log`»), но признанная слепота оставляла оператора с «причину
    не нашли». Цикл выбора проверяется настоящим `bash` по временным файлам:
    заглушка отвечает на команду целиком и «первый пустой, второй живой»
    сымитировать не может.
  - **Ротация и пустой журнал — это «не проверено», а не «писем не было».**
    Ротированный и пока пустой `maillog` обрывает цепочку `tail … || tail …`
    (rc=0 при пустом выводе) — поэтому выбор идёт по `[ -s ]`, по содержимому.
    А `journalctl` при пустом журнале отвечает не пустотой, а строкой
    `-- No entries --`: прежний код печатал её оператору как содержимое лога.
  - **Отказ — только закомбинированный статус.** Незнакомый `status=` (чужой
    MTA, новая версия postfix) считается отдельной строкой «без знакомого
    status», а не отказом: врать про беду, статус которой не понят, — тот же
    грех, что и «не проверено» → «в порядке».
  - **Отсутствие отказов не читается как «чинить нечего».** Приёмник, режущий
    спам, письмо не отбивает: он принимает его с `250 Ok` и молча кладёт в
    спам — в логе отправителя такое не светится вовсе. Поэтому сводка пишет это
    опровержение прямо под счётчиком.
  - **Тот же вывод — в двух отчётах, одной реализацией разбора.** В почтовой
    сводке — полный снимок с расшифровками; в SPF-отчёте — короткий дайджест
    («причины отказов: спам или блокировка — 2»), который подтверждает диагноз
    DNS фактами доставки. Два способа подачи одних и тех же данных, а не два
    парсера: иначе отчёты однажды начали бы по-разному считать одни строки.
    Дайджест вызывается вне цикла по доменам — иначе 25 доменов означали бы 25
    чтений лога и висящее окно GUI.
  - **Отказ подписан доменом отправления, а не только получателем.** «Письма
    отбивает Gmail» оператору бесполезно: чинит он свой домен, а не чужую
    почту. Отправителя в строке доставки нет — там только
    `to=, relay=, delay=, dsn=, status=`. Конверт живёт в ДРУГОЙ записи того же
    queue-id: `qmgr` печатает `from=<…>` в момент активации очереди, `pickup` —
    при локальной отправке (`uid=1001 from=<…>`), `smtpd` даёт логин ящика
    (`sasl_username=`), а `cleanup` пишет только `message-id` — адрес конверта
    он в лог не печатает (man cleanup(8)). Поэтому здесь честный join по
    queue-id, а не угадывание отправителя по тексту отказа.
    - **Три состояния различаются явно.** Адрес известен; `from=<>` пустой —
      автоответ и уведомление о недоставке, их нельзя приписать ни одному
      домену, конверт пуст; записи о входе письма в очередь в прочитанное окно
      не попало — это «не видно», и писать вместо этого «не ваш домен» значит
      оправдать домен ложью. Свести любое из состояний к другому — соврать
      оператору, который понесёт это клиенту.
    - **«Ваш» домен берётся из инвентаря почты сервера, а не из догадки.**
      Пометка «по вашим доменам» ставится только домену, названному панелью;
      если инвентарь для отчёта не запрашивался, так и пишется — «какие домены
      считать вашими, не проверялось». Поднять «не проверяли» до «ваши» — тот
      же грех, что и «не проверено» → «в порядке».
    - **Queue-id — шестнадцатеричная строка верхнего регистра, длина зависит от
      версии** (4 символа у старых postfix, 10–11 у новых). Жёсткая нижняя
      граница длины молча обрывала бы привязку на старом сервере, а оператор
      прочитал бы это как «письма не от наших доменов»: тихая потеря данных,
      притворившаяся выводом. Границу опустили до 4, а ложные срабатывания
      отсекает алфавит — на место идентификатор встают служебные слова
      (`postfix/smtpd[9]: warning: queue is full`, `statistics:`, `NOQUEUE:`), и
      принятый `warning` склеил бы все warning-строки сервера в одно «письмо» с
      чужим отказом. Ложный идентификатор хуже пропущенного: пропущенный
      честно печатается как «не определён».
  - **Цена не изменилась: одно чтение лога на прогон.** Индекс отправителей
    строится из УЖЕ прочитанного фрагмента — «+одна строка в отчёте» не стоит
    «+одно чтение лога». Гарды «одно чтение» стоят и на снимке, и на дайджесте
    при нескольких доменах.
- **DNS-зоны на сервере** — `mgrctl dnszone` + файлы зон BIND/nsd с serial'ом.
  - **«Сервер не является NS» печатается только тогда, когда каталоги зон
    действительно просмотрены.** Прежний поиск был `ls -1 {каталог зон}
    2>/dev/null | head -100`: пустой вывод давали «каталога нет», «каталог
    закрыт» и «зон правда нет», а отчёт выбирал самое спокойное объяснение и
    ДОПИСЫВАЛ его от себя — про чужую инфраструктуру (замер живьём: каталог
    зон без `x` давал ровно «сервер не является NS для этих доменов»). Теперь
    при непромотренных каталогах вывод помечается как предварительный, а
    причины печатаются под ним.
  - **`serial=?` означает «мы не посмотрели», а не «serial отсутствует».**
   Прежде serial читался как `parse_zone_serial(read_file_content(...) or '')`,
    где `or ''` гасило «не прочитал» в «файл пустой». Теперь рядом появляется
    строка с причиной (права, раскладка, обрыв).
- **SSL: срок действия сертификатов** — отдельно от доступности сайтов: по одному
  TLS-хендшейку на домен (не больше 25 доменов на прогон), группировка «истекли /
  истекают менее чем за 30 дней / в порядке / сертификат не получен» с подсказкой
  про Let's Encrypt для проблемных.
  - **Шапка не оставляет ложного «всё в порядке».** Раньше первая строка говорила
    «Истекло: 0, истекает < 30 дн.: 0» — и оператор, прочитавший её, уже решил,
    что с SSL всё хорошо, а блок «❓ СЕРТИФИКАТ НЕ ПОЛУЧЕН» (порт 443 молчит)
    прятался под всем списком доменов. Неполученный сертификат — не «истёк» и не
    «в порядке»: это третье состояние, и молчать о нём в первой строке — то же
    нарушение, что «не проверено → в порядке». Теперь сразу под шапкой:
    «Сертификат не получен — N: … Это не «с SSL всё в порядке», и не «истекло»:
    список таких доменов — в блоке ниже».
  - **Число берётся только из проверенных доменов**: домены за
    `HEALTH_CHECK_LIMIT` не могли «не получить» сертификат, который никто не
    запрашивал, — приписать их сюда значило бы соврать дважды (и про масштаб
    беды, и про знаменатель). Отдельной строки о непроверенных нет: «25 из 30»
    в той же шапке называет их сам.
- **Досье домена** — всё об одном домене: vhost, логи, http/https/SSL, `dig`
  A/AAAA/MX с самого сервера, ящики домена и грабля из KB FASTPANEL — домен,
  привязанный к 127.0.0.1 в `/etc/hosts` (ломает выпуск Let's Encrypt). Если
  домен почтовый, там же показывается SPF/DKIM/DMARC/PTR — **тем же кодом**, что
  и в сводном отчёте: две реализации однажды разъехались бы формулировками, и
  оператор видел бы в одном месте «DKIM нет», а в другом «DKIM ❓». У чисто
  веб-домена аутентификация не спрашивается: SPF у него может не быть намеренно,
  и ❌ напротив такого домена был бы ложным диагнозом
  - **Проверка `/etc/hosts` обязана быть выполнена, а не выглядеть выполненной.**
    Замер живьём: закрытый `0000` `/etc/hosts` и прочитанный файл без привязки
    давали побайтово одинаковое «блокеров нет». Здесь это не косметика: решение
    выпускать сертификат оператор принимает по этому блоку, и «блокеров нет»
    там, где файла не касались, стоит сорванного выпуска Let's Encrypt. Теперь
    при отсутствии чтения досье пишет, что проверка не выполнена и почему;
    привязку при этом не выдумывает (пустой список остаётся пустым).
  - **SSL подписан точным остатком, а не «истекает/нет».** Команда пробы знает о
    сертификате только «ok / не ok», и в прежнюю одну подпись сваливались три
    разные беды с разной срочностью: «истёк 4 дня назад» (браузер уже ругается),
    «истекёт через 9 дней» (чинить на неделе) и «сертификата нет вообще». Теперь
    досье пишет `❌ SSL ИСТЁК 4 дн. назад` / `⚠️ SSL осталось 9 дн.` /
    `❓ SSL сертификат не получен (https отвечает без рабочего TLS)` — **теми же
    словами, что и сводка доступности** (общий `ssl_note`), и с той же ценой:
    подпись строится из уже снятой пробы, второй пробы ради одной строки нет.
    Причина отсутствия тоже общая (`no_cert_reason`): «https не отвечает» чинят
    фаерволлом и прослушиванием 443, «отвечает без рабочего TLS» — конфигом
    vhost; одна подпись на оба случая отправила бы проверять не туда.
- **Почтовые ящики ▸** — создать, сменить пароль, удалить (свёрнуты в подменю,
  чтобы основной список не разрастался). Синтаксис — из официальной документации
  панелей: ISPmanager `mgrctl email.edit` (создание и смена пароля) и
  `email.delete`, FASTPANEL `mogwai emails boxes create/delete` (удаление по
  числовому ID из `boxes list`; смены пароля ящика в CLI FASTPANEL нет — об этом
  программа говорит прямо, а не выдумывает флаг). До отправки команды проверяются
  адрес, что домен почтовый и ящик существует (для создания — что его нет) и
  длина пароля; смена пароля и удаление требуют подтверждения. Результат
  подтверждается перечитыванием списка панели, а не кодом возврата: `rc=0` у
  mgrctl бывает и при неполной операции
- **Пароль ящика не светится в `ps`** (ISPmanager) — панель берёт его из
  окружения: `-e 'passwd=$DIAG_MAILBOX_SECRET'` (ISPsystem, «Mgrctl utility»,
  доступно с COREmanager 5.325+). Секрет пишет SFTP во временный каталог от
  `mktemp -d` (0700) с файлом 0600, команда панели его «источает» и удаляет
  каталог даже при ответе ошибки; в argv на сервере остаётся только имя
  переменной. Нет `mktemp` или SFTP — операция **отменена**, а не «тогда пароль
  аргументом»: тихий фолбэк и был тем долгом, который это закрывает. В отчёте
  показывается команда панели со ссылками `-e 'passwd=$...'` — её можно
  повторить руками, экспортировав переменную; маскирование (`passwd=***`)
  трогает только настоящие значения, например в тексте ошибки панели. CLI
  FASTPANEL принимает пароль только аргументом (`--password=`) — отчёт говорит
  об этом прямо, а не делает вид, что пароля в `ps` не было
- **Родитель ящика (`plid`) берётся из панели, а не из ввода оператора** —
  ISPsystem определяет `plid` как *parent list unique identifier*, т.е. `name`
  элемента функции `maildomain`. Программа резолвит его по `mgrctl maildomain`
  и отдаёт панели тем написанием, каким она его хранит (регистр, punycode);
  если написание в запросе отличалось — показывает это в отчёте, иначе
  оператор решит, что панель завела ящик «на другой домен». Домен, который
  postfix принимает, но панель как почтовый не знает, отсекается до отправки
  команды: панель завела бы ящик не там либо ответила невнятно. Отказ
  происходит ДО подготовки секрета (команда не ушла бы, а файл с паролем уже
  лежал бы на сервере), а «панель ответила ошибкой» не путается с «почтовых
  доменов нет» — по ошибке резолв запрещён, `plid` уехал бы наугад
- **Уборка секретов переживает кнопку «Стоп»** — `chmod`/`rm` идут служебным
  каналом (`ServerChecker.cleanup()`), который отмены не слушает: «оператор
  остановил работу» не означает «оставь файл с паролем на сервере» (пока уборка
  ходила обычным путём, она падала от отмены, и файл с паролем переживал
  операцию). Файл получает права 0600 **до** того, как в нём появляется пароль
  (`umask 077` + `: >` + `chmod 600` одной командой — между ними нет ни одного
  сетевого раунда), а перед созданием удаляется всё, что могло лежать по этому
  пути (symlink в `/tmp`). Факт удаления проверяется `[ -e ]`, а не кодом
  возврата `rm` — он молчит и когда не смог; если убрать не удалось, в отчёте
  появляется путь, который надо снести руками. То же касается временного файла
  с паролем БД во всех проверках Битрикса

### 🎛️ Управление ISPmanager
- **Диагностика панели (:1500)** — «почему не открывается» по частым причинам
  отдельно: версия (`core ispmgr -V`), процессы `core`/`ihttpd`, ответ порта с
  localhost, probe `mgrctl sysinfo` (ловит «Access to the panel is blocked by
  the administrator»), лицензия `licctl info` с подсказкой про привязку к IP,
  хвост `var/ispmgr.log`
- **Логи панели** — хвосты `var/ispmgr.log`, `var/core.log`, `var/pkg.log`
- **Разблокировать панель** — `mgrctl -m ispmgr -u` и `mgrctl -m core -u`
  (с напоминанием: блокировка бывает штатной во время `pkgupgrade`)
- **Лицензия ▾** — три операции свёрнуты в подменю, чтобы основной список не
  разрастался. Порядок внутри — «сначала смотрим, потом лечим», а ключ стоит
  последним: это единственная операция здесь, которая тратит одноразовый ключ
  - **Проверить (licctl info)** — вердикт с остатком дней («истекла N дн.
    назад» / «истекает через N дн.» / «активна»), дата окончания, срок
    обновлений, признак Trial. Дни считает **сервер** (`date -d`) — часы
    машины оператора расходятся. Молчаливый `licctl` — «чаще нет интернета»,
    а не «лицензия умерла»; `command not found` — «панель не установлена», а
    не состояние лицензии; дата есть, но серверная `date` её не поняла
    (BusyBox/BSD) — отдельная честная ветка
  - **Обновить под IP (licctl fetch)** — перетягивает лицензию под текущий IP
    (после переноса сервера) и показывает свежий `licctl info`
  - **Активировать по ключу** — `licctl fetch ispmgr <ключ>`, синтаксис из
    официального дока ISPsystem «Activating a license with a key» (формы
    `licctl activate` в документации **нет** — она встречается только в
    сторонних KB, поэтому в код не бралась и закрыта тестом). Вердикт пишется
    по **перечитанному `licctl info`**, а не по коду возврата: licctl мог
    принять ключ и не изменить лицензию. Три исхода не сводятся к двум: срок в
    будущем → активна; срок в прошлом → «ключ уже использован или IP не
    совпадает, перевыпустите ключ»; дата не определена → «активацию подтвердить
    нельзя». Ключ в отчёте замаскирован (`fetch ispmgr ***`) и вычищается из
    ответа licctl, если тот напечатал его в сообщении об ошибке. Пустой ключ
    отвергается: `fetch` без ключа — ДРУГАЯ операция (перетянуть под IP), и
    молча отправить её вместо активации значило бы тронуть лицензию не тем
    действием. Спрашивается ключ только ПОСЛЕ подтверждения, вводится со
    звёздочками, а закешированный отчёт «Проверить» принудительно устаревает:
    показать состояние «до» сразу после того, как мы его поменяли, — соврать
    оператору. У licctl нет приёма вроде `mgrctl -e $ENV`, поэтому отчёт честно
    говорит, что на время команды ключ был виден в `ps`
- Перезапуск панели (`mgrctl -m ispmgr exit`)
- Принудительное завершение процесса core (`killall core`, `pkill -9 core`)
- Обновление панели (`pkgupgrade.sh coremanager`)
- Принудительный выпуск Let's Encrypt сертификатов (`letsencrypt.periodic`)
- Отключение панели (`chmod -x /usr/local/mgr5/bin/core && killall core && killall ihttpd`)
- Отключение модуля авторизации GeoIP (`usrparam setgeoip=off sok=ok`)
- Проверка и исправление переменной PATH в crontab (для корректной работы SSL)

### 🧩 1С-Битрикс (BitrixVM)
Меню «🧩 Битрикс ▾» появляется автоматически, если на сервере найдены
`/opt/webdir` и `/home/bitrix`:
- **SSL Let's Encrypt** — срок остатка сертификатов dehydrated, хвост
  `dehydrated_update.log`, задание перевыуска ищется во всех штатных местах
  (root crontab, `/etc/cron.d`, `cron.hourly/daily/weekly/monthly`), перевыпуск
  `dehydrated -c`
- **MySQL** — `innodb_buffer_pool_size` и hit ratio InnoDB, рекомендация от объёма
  RAM (40%, округление до chunk 128M); «применить тюнинг» пишет
  `/etc/my.cnf.d/bitrix-tuning.cnf`, не трогая текущий `my.cnf`
- **Кеш** — бэкенд в `.settings.php` (`'redis'`/`'memcached'` как литерал),
  активность systemd-служб (`redis`/`redis-server`, `memcached`), `redis-cli ping`
  и размеры `bitrix/cache`, `bitrix/managed_cache`, `bitrix/merged_cache`
- **Доступ к базе** — проверка подключения реквизитами из `dbconn.php` (`SELECT 1`);
  пароль передаётся временным файлом, который получает права 0600 до записи пароля,
  и не попадает ни в командную строку, ни в отчёт; файл удаляется даже если
  операцию остановили, а если удалить не удалось — в отчёте называется путь; при
  Access denied подсказывает `SHOW GRANTS`/`GRANT`
- **Права на базу** — `SHOW GRANTS` под учёткой из `CURRENT_USER()` (хост-паттерн,
  а не `DBHost`), сравнение с минимумом ядра Битрикса, «права остались на другой
  базе» и правки по таблицам; «выдать недостающие» — `GRANT`+`FLUSH PRIVILEGES`
  под root с перечитыванием после выдачи (имена проверяются на безопасный набор)
- **Топ-таблицы базы** — 20 крупнейших таблиц по `DATA_LENGTH + INDEX_LENGTH` и
  подсказки по «мусорщикам» Битрикса (`b_user_session`, `b_cache_tag`,
  `b_stat_hit`, `b_log`, `b_sale_basket`); удалять руками `b_cache_tag` нельзя —
  чистится штатной «Очисткой кеша»
- **Права файлов сайта** — владельцы `/home/bitrix/www` (норма `bitrix:bitrix`),
  world-writable файлы и запись в `bitrix/cache`, `bitrix/managed_cache`,
  `bitrix/data`, `upload`; «починить» — `chown -R` + 755/644 + `g+w` на `upload`
- **PHP** — версия, параметры `/opt/php*`, обязательные модули из check.php
- **Cron-агенты** — наличие задания `cron.sh` (без него агенты крутятся на каждом
  хите); «установить в crontab» дописывает рекомендуемую строку с бэкапом crontab
  и проверкой после записи, дубликат не создаёт
- **Почта** — состояние postfix, глубина очереди `mailq`, хвост `/var/log/maillog`;
  «отправить тестовое письмо» — отправка через `sendmail -t` с разбором записи
  postfix по точному получателю (`status=sent`/`bounced`/в очереди): `rc=0` —
  это «принято», а не «дошло»

### 💾 Управление Swap
- Создание swap-файла с указанием размера (проверка свободного места)
- Добавление swap в fstab для автоматического подключения

## 🚀 Установка

Самый быстрый способ — скачать готовый бинарник для Linux из [Releases](https://github.com/DrFaustos/techsupp_diagtool/releases). Ниже — установка из исходников.

### Требования
- Python 3.7+
- pip
- Tkinter (обычно входит в состав Python)
- Для работы с Tkinter в Ubuntu: `sudo apt install python3-tk`

### Шаги установки

Клонируйте репозиторий:
```
git clone https://github.com/DrFaustos/techsupp_diagtool.git
cd techsupp_diagtool
```

Создайте виртуальное окружение:
```
python3 -m venv venv
source venv/bin/activate       # Linux/Mac
venv\Scripts\activate          # Windows
```

Установите зависимости:
```
pip install -r requirements.txt
```

Запустите программу:
```
python3 main.py
```

### Запуск тестов

```
venv/bin/python -m pytest tests/ -q                # все тесты
xvfb-run -a venv/bin/python -m pytest tests/ -q     # со смоуком GUI под X11
```

## 📝 Пример использования

1. Введите IP-адрес сервера, порт (по умолчанию 22), пользователя (по умолчанию root)
2. Введите пароль или укажите путь к приватному ключу (нажмите «Обзор»)
3. Выберите тип панели управления или оставьте «Авто»
4. Нажмите «Подключиться»
5. После успешного подключения:
   - Кнопка станет красной с текстом «Отключиться»
   - Все кнопки диагностики активируются
   - Появится панель управления ISPmanager (если определена)
6. Нажмите «Полная диагностика» для комплексной проверки
7. Используйте отдельные кнопки для детального анализа конкретных параметров
8. Для отправки произвольной команды используйте нижнее поле ввода
9. Для просмотра истории команд нажмите «История»

## 🔧 Поддерживаемые панели управления

### FastPanel
- Определение по наличию `/usr/local/fastpanel/bin/fastpanel`
- Список сайтов, почтовых доменов и ящиков — CLI панели `mogwai sites list` /
  `mogwai emails domains list` / `mogwai emails boxes list`; конфиги
  `/etc/nginx/fastpanel2-available/*/*.conf` — запасной источник
- Логи сайтов в `/var/www/пользователь/data/logs/*.log`
- Поддержка суффиксов `-frontend` и `-backend`
- Диагностика :8888 — юнит (`fastpanel2-engine`/`fastpanel`) + journal,
  **наличие пакета fastpanel2** (404 на :8888 по KB FASTPANEL чаще всего означает
  пакет, снятый менеджером зависимостей), порт с localhost, лог, hostname без точки
  - **Отказ обязан называть своё основание.** Прежний
    `systemctl cat ЮНИТ 2>/dev/null | head -1` на вопрос «есть ли служба панели»
    отвечал пустотой одинаково в трёх случаях: юнита нет; systemd говорить не
    может (контейнер, chroot, мёртвый bus); бинарника `systemctl` нет. Пайп с
    `head` забирал себе код возврата (он доволен всегда, rc=0 везде), а
    `2>/dev/null` глушил единственную строку с причиной. Замер живьём на хосте
    без systemd: `fastpanel_unit` → `None`, `fastpanel_restart` → «Служба панели
    не найдена», команда перезапуска при этом НЕ отправлялась. Теперь команда
    `systemctl cat ЮНИТ 2>&1` (rc принадлежит systemctl), и отчёт различает
    «не найдена» (так ответила система) и «не проверено» с названной причиной —
    это разные действия: ставить панель против чинить доступ к systemd.
    Разбор по rc идёт ПЕРВЫМ: `rc=127` печатает «No such file or directory», и
    без этого «systemctl нет» превратилось бы в «юнита нет».
  - **Пакет: «НЕ найден» ≠ «не проверено».** Прежний
    `dpkg -l 2>/dev/null | grep -i 'fastpanel2' | head -3` терял и причину
    (`2>/dev/null`), и код возврата (конвейер отдаёт rc последней команды —
    `head` доволен всегда): на хосте без `dpkg` (rc=127) и без прав на базу
    пакетов (rc=2) он возвращал rc=0 с пустотой — ровно ту же, что при снятом
    пакете, — и отчёт советовал `apt install fastpanel2` на машине с ЦЕЛОЙ
    панелью. Теперь `LC_ALL=C dpkg -l 'fastpanel2*' 2>&1` без пайпа, вердикт
    выносится ТОЛЬКО кодом возврата (текст локализован: в русской локали `dpkg`
    пишет то же по-русски при том же rc), шаблон в кавычках (без них shell
    раскрывает его в имена файлов и `dpkg` вводит в заблуждение своим rc=0), а
    `rpm` зовётся как `rpm -q`, не `rpm -qa` (у `-qa` «нет совпадений» — rc=0 с
    пустотой, неотличимой от обрыва). Отчёт различает три состояния: найден (со
    строкой пакета и версией), «пакета нет» (rc=1 — настоящая причина 404 из
    KB FASTPANEL) и «не проверен» с цитатой ответа системы. Цена: **1 команда
    вместо 2** на Debian-хосте.
  - **Логи панели** ищутся тем же примитивом состояния каталога, что и конфиги:
    «нет прав на каталог логов» и «каталога нет» — два ответа с
    противоположным лечением, прежний `ls -1 … 2>/dev/null` давал на оба
    «Логи панели не найдены по путям». Пустой **прочитанный** каталог жалобы не
    даёт: «логов нет» — честный ответ.
  - Цена честности: **команд ровно столько же** (по одной на путь и на юнит),
    слепых `2>/dev/null` в этих функциях — 0.
- Сброс пароля `fastuser` через `mogwai chpasswd` (проверка длины ≥ 8 на стороне
  программы, предупреждение что пароль был виден в `ps`)

### ISPmanager

## 🔒 Безопасность

- Пароли не сохраняются и не логируются (очищаются из памяти после подключения)
- Поддержка SSH-ключей для безопасной аутентификации
- Проверка ключа хоста (RejectPolicy — неизвестные хосты отклоняются)
- Все операции выполняются через зашифрованное SSH-соединение
- Создание резервных копий перед изменением конфигурационных файлов в каталоге `/root/tech_support/`:
  - `configs/имя_файла.ГГГГММДД_ЧЧММСС.bak` — конфигурационные файлы
  - `dns/имя_файла.ГГГГММДД_ЧЧММСС.bak` — DNS (/etc/resolv.conf)
  - `crontab/crontab.ГГГГММДД_ЧЧММСС.bak` — crontab
  - `configs/etc_ГГГГММДД_ЧЧММСС.tar.gz` — архив /etc перед заменой IPv6
- Подтверждение всех критических операций перед выполнением

## 🔧 Устранение неполадок

### Ошибка `No module named 'tkinter'`

Установите Tkinter:
```
sudo apt install python3-tk        # Ubuntu/Debian
sudo yum install python3-tkinter   # CentOS/RHEL
```

### Ошибка подключения

1. Проверьте доступность сервера: `ping IP`
2. Проверьте SSH-порт: `telnet IP 22`
3. Убедитесь, что используете правильные учётные данные
4. Попробуйте подключиться вручную: `ssh user@IP`

### DNS не меняется

Проблема может быть в:
- **systemd-resolved** – настройте через «Изменить DNS» (определяется автоматически)
- **Прямое редактирование** – если systemd-resolved не активен, «Изменить DNS» пишет в /etc/resolv.conf напрямую

## 📦 Сборка исполняемого файла (опционально)

Готовый standalone-бинарник для Linux (x86_64) лежит в
[Releases](https://github.com/DrFaustos/techsupp_diagtool/releases): скачать, сделать исполняемым и запустить.

```
chmod +x ServerDiagnostic
./ServerDiagnostic
```

Зависимости не нужны: Python, Tkinter и библиотеки уже внутри.
Бинарник собран на Ubuntu 24.04 (glibc ≥ 2.14), под другие ОС соберите сами.

Пересобрать под свою систему:

```
pip install -r requirements.txt pyinstaller
pyinstaller ServerDiagnostic.spec
```

Собирать нужно именно по спеке — руками через `--collect-all` проще потерять
раскладку Tcl-модулей. В `ServerDiagnostic.spec` разложены: темы `ttkbootstrap`
(пакет грузит их из своего каталога), `PIL._tkinter_finder` (без него окно падает
на старте с `invalid command name "PyImagingPhoto"`) и Tcl-модули `.tm` в
`_internal/tcl8/<версия>/` (иначе на машине без системного Tcl старт гибнет с
`::msgcat::mcmset: invalid command name`). Раскладка `.tm` закрыта тестом
`tests/test_spec_tcl.py`.
